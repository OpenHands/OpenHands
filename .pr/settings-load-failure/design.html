Design doc · PR #19966 · fix/settings-load-failure

A failed settings load is now observable

The three silent fallback sites in getSettings are replaced by a strict contract: settings surfaces render an explicit load-failure state with a bounded retry, the four legitimately lenient callers move to a new getSettingsWithDefaults, and saving is guarded while the load state is unknown.

1The failure the GUI could not see

On main, getSettings caught every load failure and returned syncDerivedSettings({}) — fabricated defaults, indistinguishable from real ones settings-service.api.ts:599-637 (before). The dangerous consequence: opening settings during a transient backend failure, then saving, writes those fabricated defaults over the user's real persisted settings.

★ The GUI settings surfaces must never mistake "could not load" for "the user has empty settings" — that sentence is now the documented contract of getSettings settings-service.api.ts:596-604.

2API before → after: strict vs lenient

Exactly four callers legitimately wanted best-effort defaults — conversation launch, default-agent-profile migration, LLM-profile rename/delete — and were moved to getSettingsWithDefaults settings-service.api.ts:641-656. The cloud branch keeps best-effort behavior there (documented inline).

ⓘ A 404 ("server has no stored settings yet") still resolves to success-with-defaults. Only transport/5xx failures became observable.

3What renders when the load fails

useSettings now fabricates an explicit error state — 404 maps to success-with-defaults, real failures map to an error flag with retry capped at 3 use-settings.ts (the old unbounded retry predicate was its own landmine). Settings surfaces render the new SettingsLoadError panel settings-load-error.tsx with SETTINGS$LOAD_FAILED / SETTINGS$RETRY strings across all locales translation.json.

4Save guard: fabricated defaults cannot be persisted

use-save-settings refuses to save while settings are in a failed/unknown load state use-save-settings.ts — so the failure scenario can no longer destroy the user's real settings.

⚠ Conversation launch deliberately still uses defaults (getSettingsWithDefaults): a settings hiccup must not block the user from working; it must only stop them from silently overwriting state.
