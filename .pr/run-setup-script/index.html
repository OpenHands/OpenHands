Auto-run .openhands/setup.sh at conversation start

Branch feat/run-setup-script-at-conversation-start · head 10937a0a · merge-base 311dc1be · 10 files · +1722 / −99

1 · What changed

On a local backend, starting a conversation now detects <workspace>/.openhands/setup.sh, runs it through the conversation's own terminal before the first user turn, and then sends the withheld first message. Because the script is sourced in the agent's terminal session, the environment it sets (export, cd) is still there when the agent runs its later commands — which a one-shot bash setup.sh could never achieve.

★ Compatibility & risk. Canvas adds no new server route. It consumes POST /api/conversations/{id}/execute_tool from OpenHands/software-agent-sdk#6099, gated at runtime on the direct_tool_execution_v1 capability (src/api/setup-script-service.ts:24).

The feature is purely additive: cloud backends, servers without the capability, a pinned client without executeTool(), and workspaces with no script all take the unchanged existing path. Nothing is required of a deployment that does not want setup scripts.

Compatibility: additive. Gated on the direct_tool_execution_v1 server capability and a client that exposes executeTool(); otherwise the service reports skipped. compatibility.minimumAgentServer is deliberately not raised — the route ships in the same package version as servers that predate it, so a version floor would reject whole backends instead of just skipping setup.

before createConversation posted the payload including initial_message, which is what starts the run server-side.  →  after it withholds initial_message when a plan exists (:729), creates the conversation, re-probes the assigned data.workspace.working_dir (:761), runs setup (:765), then sends the withheld message with run: true (:832).

Why re-probe? A new_worktree launch returns a different directory (/tmp/conversation-worktrees/<id>/<repo>). The pre-create probe only decides whether to withhold; setup must run against the directory the agent will actually use, or the user's own checkout would be polluted while the worktree stayed unprovisioned.

Withholding the first message makes it a separate send that can fail after the conversation exists. The mutation now recovers that case: on ConversationFirstMessageError it reports the conversation that does exist as success and leaves the user's message as an errored pending bubble on it, so retry resends to the same conversation instead of creating a second one. Recovery also best-effort re-stamps the launch profile and plugin snapshot, and classifies a 4xx (refused, safe to retry) vs an ambiguous failure (bubble stays sending until the server echo or the pending-message watchdog resolves it).

before the local worktree fallback treated any createChild error as "the worktree could not be created" and retried with shared isolation.  →  after a ConversationFirstMessageError is recovered onto the created child instead (recoveredFirstMessageLaunch, :277): the worktree was cut fine, so retrying would create a second conversation, strand the first idle, and silently downgrade the isolation the caller asked for. The result carries a first_message_note so the delegating agent learns the child's task never started. A non-recoverable error still falls back to shared as before.

onSetupScriptProgress (:240) relabels the create toast to STATUS$SETTING_UP_WORKSPACE (already present in all 16 locale catalogs) while the bootstrap runs.
