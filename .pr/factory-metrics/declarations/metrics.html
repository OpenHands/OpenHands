Metrics: how a key counts

A metric is a key a plugin reports. Before any card, the key decides what a fact means and when it counts. This page shows the two kinds of key, the fields a plugin must send for each, and what the service refuses.

Every card type reads these keys. A rate card is only correct if the key counts the way the plugin expects.

01

Increments

Every fact counts. The default. Five examples.

An increment is an amount that happened: a PR merged, 300 lines changed, a review that passed. Each fact is one thing that happened once. The facts add up.

The simplest increment. The plugin sends the value 1 for each merged PR. 2 The card sums the facts in the window. 1 3 Title and hint come from the card and the key, as on the Count page. The two highlighted fields in the request are what make the count right. occurred_at says when the PR merged. dedupe_key names the event, so that a retry does not count it twice (example B).

The plugin sends · the same request as example A, a second time
curl -X POST "$AUTOMATION_OUTCOME_URL" ... \
  -d '{
    "values": [{ "key": "prs_merged", "type": "number", "value": 1 }],
    "occurred_at": "2026-11-24T16:20:00Z",
    "dedupe_key": "acme/api#1425"
  }'
→ 201 {"stored": 0, "duplicates": 1}  checked

A dedupe_key is unique for a factory and a key, across all automations. The second request is not an error. The answer says duplicates: 1 and stores nothing. So a script can send again after a timeout, and a run that is retried cannot count a PR twice. Use a name that belongs to the event, such as the repository and PR number. A run id is wrong: a retried run has a new id.

Without occurred_at a fact counts when the service gets it. That is right for a plugin that runs when the event happens. It is wrong for a nightly scan that finds yesterday's PRs: they would all count on the day of the scan, and a day or week card would show a false spike. A scan must send occurred_at. A time more than five minutes in the future is refused (sheet 04).

The value does not have to be 1. Each fact carries an amount, and sum adds the amounts. count would give 4 and ignore them. The same key can feed a total card (sum), an average card (avg) and a count card (count).

A boolean key is always an increment. A total must be a number, and the registry refuses semantics: total on any other type. The percent card (a later page) divides count_true by count.

02

Totals

One number for each period. The latest report wins. Five examples.

A total is the number for a whole period, such as "PRs merged on 24 Nov". The plugin may report it once, or again and again as it learns more. For each automation, set of dimensions and period, only the last report counts. The earlier ones stay in the history and drop out of every card.

A total counts at the start of its period. It needs a number type and a grain: hour, day, week or month. The plugin sends period in the format of the grain. It must not send occurred_at or dedupe_key.

The card reads · whole days, 18 to 24 Nov
GET .../outcomes/aggregate?key=merged_daily&operation=sum

The plugin counts for itself and reports the answer. That suits a job that queries GitHub once a day: it does not have to track which PRs it has seen. 2 sum adds the latest total of each day. count here would be 7, the number of days with a fact, not the number of PRs. The window is drawn as whole days. A rolling 7d window cuts the first day off, as the Count page shows.

This is why a rate does not depend on how often the plugin runs. A plugin that reports every hour, or three times a day, gives the same card as one that reports once. Only the last report of the period counts. "Last" means last received, never the plugin's own clock. An older report that arrives late does not undo a newer one.

The period text must match the grain. A week is an ISO week, YYYY-Www, and starts on Monday in UTC. A month is YYYY-MM. An hour is YYYY-MM-DDTHH. The service stores the start of the period, so a week card and a day card agree about which Monday a fact belongs to.

What the service gives today · window of 1 day, 24 Nov 09:30 to 25 Nov 09:30

A count of open PRs is a level. Adding two hourly levels makes no sense, and max is wrong as soon as the level falls. The card needs the value of the latest period: a last aggregation. It does not exist. Until it does, a level card can only show a window so short that it holds one period, and that card shows "No data" when the latest report is not in the window yet.

03

Dimensions

Labels on a fact, such as the repository. Four examples.

A fact can carry up to eight labels. A later total replaces an earlier one only when the automation, the period and every label match. Two facts with different labels do not replace each other.

    "period": "2026-11-24",
    "dimensions": { "repo": "acme/api" }
... same, value 3, "dimensions": { "repo": "acme/web" }

The card has no repo setting, so it adds all repositories. The repository is a label on the fact, not a different key. The third request replaces the first, because the repository is the same. It does not touch acme/web. Dimensions are stored in #818. The card cannot yet filter or group by them (example C).

D · Limits on labelsopen PR #818
D · limits
at most 8 labels
name: letters, digits, _ . -, up to 40
value: 1 to 64 characters
The plugin sends · an empty value
... "period": "2026-11-25", "dimensions": { "repo": "" }
→ 422  Dimension 'repo' must be 1 to 64 characters  checked

Labels are for a few short values, such as a repository, a team or an environment. A PR number or a title is a bad label: every value is a new set, and a total for each one would never be replaced. Labels are stored with sorted names, so {"a":"1","b":"2"} and {"b":"2","a":"1"} are one set.

04

Requests the service refuses

What a plugin gets back when the request does not fit the key. Eight cases.

Each key accepts only the fields that fit its kind. A wrong request answers 422 with the format it wanted, and nothing is stored. A plugin should log the message. A whole request fails together: if one key of several is wrong, none is stored.

The plugin sendsAnswer checked
1A total with no periodOutcome key 'merged_daily' is a total. Send period as YYYY-MM-DD, for example 2026-11-24
2A period in the wrong format for the grainperiod '2026-11-24' is not a week period. Use YYYY-Www, an ISO week, for example 2026-W48
3A total with dedupe_keyOutcome key 'merged_daily' is a total. A later report for the same period replaces the earlier one, so occurred_at and dedupe_key do not apply
4A total with occurred_atThe same message as case 3.
5An increment with periodOutcome key 'prs_merged' is an increment. period applies only to totals
6A period that has not begun, or an occurred_at more than five minutes aheadOutcome key 'merged_daily' cannot count at a future time
7A key the factory does not have, or with another typeOutcome key 'nope' is not registered with type 'number'
8An empty label valueA validation error: Dimension 'repo' must be 1 to 64 characters
Cases 1 to 5 mean the plugin and its manifest disagree about what the key is. The fix is in one of the two. A key cannot change type, semantics or grain once it has facts: PUT /outcome-keys/{key} answers 409. Two plugins in one factory that declare the same key must declare it the same way. The install step proposed here would refuse the second one.
05

Increment or total

How to choose for a key.
The plugin…UseWhy
sees each event once, as it happens, and can name itincrement with dedupe_keyRetries are safe. The service counts for you. A card can slice the count by any window.
scans on a schedule and finds events after the factincrement with occurred_at and dedupe_keyA scan that overlaps its last run finds the same events again. The key makes them one.
queries a system that already holds the answer ("merged yesterday")total with grain: dayThe plugin does not have to track events. It may report as often as it likes.
measures a level ("open PRs now")total with grain: hour or dayEach report is a new reading that replaces the last. A level card needs last.
reports true or falseincrementA total must be a number.
