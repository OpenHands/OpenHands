01

Reading guide

How to read the pins and the labels on the sheets that follow.

Pins

A pin joins a line of the manifest to the part of the card it controls. The numbers mean the same on every sheet.

1The card title. It comes from the card, not from the metric.
2The value. The metric aggregation and the card window decide it together.
3The hint line. It comes from the metric description.
4The link. The whole card becomes a link, and a chevron shows.
5No place on the card. It says where the number comes from (from).
a bLetters mark separate cards when one example has more than one card.

Labels

Two kinds of label sit at the top right of each example. One says if the manifest field is proposed. The other says if the service can do the work today.

new new: manifestA manifest field proposed by this page. The manifest schema does not have it today. It rejects fields it does not know.
mergedThe service does this work in OpenHands/automation main today, for example an aggregation.
open PRThe work is in an open pull request and not on main.
gapThe card needs it and no pull request provides it yet. The text after the colon says what is missing.

    "key": "reviews-total",
    "title": "Reviews posted",1
    "source": { "type": "outcomes", "metric": "reviews_posted" },
    "display": "number",
    "window": "all"2
  }]
}

The simplest Count card. The plugin declares one metric and one suggested card. 1 The title comes from the card. 2 The value is the sum of reviews_posted over the window, and here the window is all. 3 The hint line is the metric description. label names the metric in lists and menus, and the card does not use it. 5 from says where the number comes from: the reviews field of the run result. It has no place on the card. A plugin that posts its own values leaves from out. The card has no link, so it shows no chevron and no hover style.

One metric, two cards. The metric says what the number is. A card says how to show it. Cards a and b read the same metric with different windows. Remove card b and the metric and card a stay. Remove the metric while a card uses it, and the service refuses with 409.

Card keys are unique in a factory. Install adds a suggested card only when its key is free, and never overwrites a card an admin has edited. A manifest that declares outcomes fails to install on a service that does not support it.

Aggregations

How the facts in a window become the number on a card. Eight examples.

An aggregation turns the facts in the window into one number. The metric names a default, and a card can set its own. Each example below is a card on the left and the manifest lines that set it up on the right. The two metrics come first, with their facts. The facts do not change from one example to the next.

      "type": "number",

A metric holds facts. This one gets one fact for each merged PR. The window holds four facts. The highlighted aggregation is the default for cards that do not set their own. Every number on this sheet comes from these four facts, so you can check each one by hand.

Which aggregation fits which metric type

Metric typeAggregations
numbersum avg min max count gap last
booleancount_true count_false count
string datetime jsoncount
With no facts in the window, sum, avg, min and max have no value and the card shows —. count, count_true and count_false give 0. A card never shows 0 for a number that is missing. A card whose aggregation does not fit its metric type is refused with 422. This is a proposed rule. Percentiles such as p50 and p90 are a gap and are not on this sheet.
