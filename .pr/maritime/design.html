Agent Canvas · Add Backend → Providers

Maritime as a sandbox provider

A second entry in the Providers tab. Each OpenHands agent runs in its own Maritime micro-VM, reached directly at its public HTTPS hostname, so the integration is the DigitalOcean one minus the tunnel and the proxy.

1. What changed

Add Backend → Providers lists Maritime under DigitalOcean when a Maritime bridge is present (always in the desktop app; in the web build when the server opts in with MARITIME_WEB=1). Signing in with a Maritime API key shows the account's plan and the OpenHands agents Canvas created on it. Creating or opening one registers that agent's agent-server as an ordinary kind: "local" backend and lands the user in it.

★ Additive. No existing behavior changes. The only edits to shared code are: Backend.maritimeAgentId? (optional field), the Providers tab rendering a list of available providers instead of one hard-coded button, a non-active Maritime backend getting the same "probe once" treatment as a non-active MARS session in useBackendsHealth, and the DigitalOcean web bridge's request guards moving into scripts/web-bridge-guards.mjs unchanged.

3. Bridge contract

MaritimeBridge in src/api/maritime/maritime-bridge.ts, served by createMaritimeBridge in scripts/maritime-bridge.mjs (IPC channels MARITIME_IPC; web RPC allow-list is exactly the same set).

getAuthState()            -> {isSignedIn, isSaved, storage}        no network, never the key
saveApiKey({apiKey})      -> verified with GET /api/v1/account/limits, then kept
signOut()                 -> drops the API key (agents' session keys stay)
getAccount()              -> {plan, machines, awakeMachines, maxAwakeMachines, minMemMb, maxMemMb}
listAgents()              -> MaritimeAgent[]  (externalId = openhands-agent-canvas; hasAccessKey per agent)
createAgent({name, memMb, origin}) -> {agentId, name, host, sessionApiKey} once Maritime says active
openAgent(id)             -> same, after waking a sleeping/stopped agent
resetAccessKey(id)        -> new OH_SESSION_API_KEYS_0 + restart, same return
sleepAgent(id), deleteAgent(id)

  "imageName": "ghcr.io/maritime-sh/openhands-agent-server:<versions.agentServer>",
  "exposedPort": 8080, "publicWeb": true, "hasWebUi": false, "healthCheckPath": "/health",
  "memMb": 4096, "vcpus": 2, "idleTtlSeconds": 1800,
  "initialEnvVars": [
    {"key": "OH_SESSION_API_KEYS_0", "value": "<random 256-bit>", "isSecret": true},
    {"key": "OH_SECRET_KEY",         "value": "<random 256-bit>", "isSecret": true},
    {"key": "OH_ALLOW_CORS_ORIGINS_0", "value": "<Canvas origin, only if not loopback>"} ] }
  • Image. The published ghcr.io/openhands/agent-server:<v>-python plus a launcher that binds $PORT: Maritime routes the agent's hostname (HTTP and WebSocket) to $PORT, 18789 today, and the stock image binds 8000. Built per agent-server release, after a smoke test, by maritime-sh/openhands-agent-server. The tag follows config/defaults.json versions.agentServer, so Canvas creates the version it pins.
  • publicWeb. A private Maritime URL needs a Maritime link cookie, which a CORS preflight never carries. The agent-server's session key is the guard, as for every remote backend.
  • Readiness. The bridge polls Maritime until active; the renderer then runs validateLocalBackend (settings + server info through the typed client) until it answers, before registering the backend.

Maritime shows secret env vars masked, so a session key cannot be read back from Maritime. An agent without one on this machine offers Set new access key (confirmed): new OH_SESSION_API_KEYS_0 via POST /api/agents/{id}/env, then POST /restart. Conversations and settings survive on /data.

The web bridge reuses the DigitalOcean bridge's guards verbatim (scripts/web-bridge-guards.mjs): session key required on every RPC, loopback only without a key, cross-origin and foreign Host refused. A new agent's CORS origin comes from the request in the web build, not from the page.

6. Cost and lifecycle

  • Every HTTP request to an agent's hostname wakes it and resets Maritime's idle timer, so a non-active Maritime backend is probed once and never polled (useBackendsHealth, same rule as MARS).
  • Maritime sleeps an agent after idleTtlSeconds (1800) without HTTP traffic; a busy CPU keeps it awake, open WebSocket frames alone do not. Sleep keeps memory; the next request wakes it in about a second.
  • Delete removes the VM and its disk on Maritime first, then the agent's backends in Canvas, so a refused delete leaves a working backend.

8. Risk and what a live test must confirm

The captures in this PR are mock mode. These need a real Maritime account before the PR leaves draft:
  • The image boots on Maritime and the agent-server answers at webUrl, REST and the event WebSocket included.
  • CORS: the agent-server accepts the desktop origin (http://localhost:8000) through Maritime's proxy, preflights included.
  • Sleep and wake keep a conversation and its terminal intact.
  • /data is writable by the image's non-root user (the launcher falls back to the image's home and says so if not).
  • Known gap: VS Code and the worker ports are not reachable (Maritime publishes one port per agent), so Canvas features that open those show nothing on a Maritime backend.
