Bug fix · Agent Canvas frontend

Unify the archived conversation predicate

The conversation list had two independent notions of "archived" that disagreed: the status dot dimmed and labelled a missing-runtime row "Archived", while list visibility, the "Archived" chip, and the ⋮ menu still treated it as active. This PR derives every archived presentation from one predicate, and stops conflating a missing runtime with an errored one.

10 files  ·  +233 / −16  ·  no dependency or wire-contract changes  ·  fixes #18155

★ Key takeaway. A row is now "effectively archived" when the user archived it or its runtime is missing and non-resumable; that one predicate drives list visibility, the "Archived" chip, and the menu direction. ERROR keeps its red "Error" indicator and is never archived. The single new symbol is isEffectivelyArchivedConversation · src/utils/conversation-archive-status.ts:38.

1The bug: two archived notions disagreed

After an automation run finished, its conversation's runtime was torn down and could not be resumed. The backend reported sandbox_status: "MISSING" (Cloud) or runtime_info.runtime_status: "missing" + can_resume: false (local). The row then rendered the gray archive icon, tooltip "Archived", and a dimmed title — but it stayed in the default list, showed no "Archived" chip, and its ⋮ menu still offered "Archive".

⚠ Also wrong. isArchivedSandboxStatus returned true for both MISSING and ERROR, so an errored runtime got the dimmed title and skipped its WebSocket — even though the status dot renders ERROR as a red "Error" dot, not as archived.

2One predicate, two concerns split apart

The old single helper mixed a runtime concern (is the sandbox gone?) with an archive concern (should this row present as archived?). The fix names each:

ConcernSymbolReturns true forDrives
Runtime unavailable (read-only)isRuntimeUnavailableSandboxStatusMISSING, ERRORWebSocket gating, chat input, git/panel toggles
Missing & non-resumableisMissingSandboxStatusMISSINGstatus dot "Archived", dimmed title
Effective archivedisEffectivelyArchivedConversationexplicit archive or MISSINGlist visibility, "Archived" chip, ⋮ menu direction
ⓘ Why ERROR stays read-only but not archived. An errored sandbox is also gone and cannot be resumed, so its runtime-backed affordances remain read-only (websocket-provider-wrapper.tsx:101). But it is not "archived": it keeps the red Error dot and never gets the chip, so it is not conflated with MISSING.

3API before → after

Before

// one helper, two meanings
export function isArchivedSandboxStatus(
  s: SandboxStatus | null | undefined,
): boolean {
  return s === "MISSING"
      || s === "ERROR";
}

// list/chip/menu read the store, not this
archivedIdSet.has(conversation.id)

After

export function isMissingSandboxStatus(
  s: SandboxStatus | null | undefined,
): boolean { return s === "MISSING"; }

export function isRuntimeUnavailableSandboxStatus(
  s: SandboxStatus | null | undefined,
): boolean {
  return s === "MISSING" || s === "ERROR";
}

export function isEffectivelyArchivedConversation(
  s: SandboxStatus | null | undefined,
  explicitlyArchived: boolean,
): boolean {
  return explicitlyArchived || isMissingSandboxStatus(s);
}

Verdict: internal refactor. No exported API, wire contract, or TypeScript-client normalization changes; the renamed helpers are module-internal to Canvas.

4Per-file changes

✏️ The predicate — src/utils/conversation-archive-status.ts

Splits the overloaded isArchivedSandboxStatus (MISSING||ERROR) into isMissingSandboxStatus (MISSING), isRuntimeUnavailableSandboxStatus (MISSING||ERROR), and the new isEffectivelyArchivedConversation (explicit || MISSING).

✏️ The panel — conversation-panel.tsx:208

Adds one isRowArchived(conversation) callback. The display filter, the isArchived handed to cards, and the ⋮ menu direction all call it instead of archivedIdSet.has(id). Delete/prune logic still reads the unfiltered loaded set, so hiding a row never shrinks what can be deleted.

The ⋮ menu offers exactly one direction per row: Archive until the row is effectively archived, then Unarchive. This holds for a runtime-derived archive too: "Unarchive" clears the user's explicit archive intent (if any) and does not resume the runtime, so a missing-runtime row stays archived while its runtime is missing and non-resumable — never a dead Archive direction nor a broken promise.

✏️ Status dot & dimmed title

conversation-status-dot.tsx, conversation-card-header.tsx, the hover preview, and the compact row all take the row's effective archived state (isArchived), not the raw sandbox status, so an explicitly archived row streams the gray archive dot and dimmed title even though its runtime is fine, and the dot can never disagree with the "Archived" chip. A missing sandbox is still inferred from sandboxStatus for callers that only have that, and an unarchived ERROR row keeps its red "Error" dot and badge.

✏️ Read-only gate

use-is-archived-conversation.ts:15 and websocket-provider-wrapper.tsx:101 keep using isRuntimeUnavailableSandboxStatus (MISSING still read-only; ERROR stays read-only too, unchanged). The hook's docblock now states it is the read-only gate, not the archive predicate.

⚙️ Mechanical

compact-conversation-row.tsx gains an isArchived prop forwarded to the card preview so the compact layout shows the same chip.

ⓘ Where MISSING actually comes from. The local (non-Docker) agent server reports every catalog conversation as runtime_status: "available", so it never yields a MISSING row; the adapter maps MISSING from a Cloud sandbox_status or a Docker-runtime runtime_info.runtime_status: "missing" with can_resume: false (the conversation_runtime: "docker" mode). That mapping is pinned by agent-server-adapter.test.ts (missing+non-resumable → MISSING; missing+resumable → null), and the fixtures here use that contract. The presentation side is therefore exercised end-to-end against the real Canvas with the backend-shaped payload.
