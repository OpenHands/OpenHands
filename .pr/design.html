Design doc · feat(feature-policy)

Startup feature policy, gating Add Backend first

An operator can now list Canvas controls to turn off in an environment variable. The launcher validates that list once at startup and injects it into the page. One React hook, useFeaturePolicy(), answers "is this control allowed?" wherever the UI decides to render it. This PR ships that plumbing plus exactly one rule, backends.add, so reviewers can judge the pattern on a single, small call site.

1One policy, one gated button

★ With no policy configured, nothing changes. Every feature is on unless its ID is listed, builds never bake a policy in, and the only UI edit is one condition in backend-selector.tsx:241.

The motivating case: someone runs Canvas on a small VM for a few people behind their own sign-in. They set it up fully, then want those users to focus on chatting with an agent instead of reconfiguring the instance. Today the only lock Canvas has is lockToCloud, a single-purpose switch. This PR adds a general one.

5Rules grow one element at a time

The catalog starts with a single entry on purpose. Each next rule is its own PR or commit, so a reviewer can check exactly what one ID hides and how.

// config/features.json
{ "id": "backends.add",
  "description": "Hides \"Add Backend\" in the backend selector menu (sidebar, expanded and collapsed)." }

Adding or extending a rule takes four edits:

  1. Add the ID to config/features.json, or extend an existing ID's description to name the new element.
  2. Add it to FEATURE_IDS in feature-policy.ts:5. A contract test fails if the two lists differ (feature-policy.test.ts:102).
  3. Gate the element with featurePolicy.isEnabled("…") where the UI already decides whether it renders.
  4. Add a test that renders the element under FeaturePolicyProvider.

Natural next candidate: extending backends.add to the Manage Backends window's add button, which would make the ID cover every add-backend path in the sidebar.
