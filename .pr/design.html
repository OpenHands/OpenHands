Design doc

Reply to a message

A user can reply to any message in the chat. The replied-to message travels inside the outgoing user text as a start-anchored envelope, so the model receives it as ordinary context and every renderer rebuilds the quote card from the message itself. Nothing on the wire changes: no SDK field, no agent-server release, no compatibility floor.

1What changed

Before this branch there is no way to point at one message. A follow-up arrives as a plain user turn, and the model resolves "that" from event order. This PR adds three things: a Reply action per bubble, an armed quote in the composer, and a pure text module that owns the quote format.

★ The whole feature is a text convention plus a store. Because the quote lives in the message body, pending, sent, and reloaded bubbles all render identically with no server support, and the feature works on Local and Cloud backends as well as OpenHands and ACP agents.

2The message format

The envelope is anchored at position 0 of the user text, the same convention splitInlineThink already uses. Tokens are locale-independent program identifiers, never i18n keys.

<reply-to id="<source event id>" source="user|agent" truncated="false">
<quoted body, verbatim, inner envelopes stripped>
</reply-to>
<user's follow-up text>

Three properties make this safe to introduce without a migration:

  1. The parser degrades. A malformed or absent envelope renders as plain text, never a crash (message-quote.ts:89).
  2. Depth is capped at two. Quoting a message that is itself a reply strips the inner envelope first (stripReplyEnvelopes, line 155), so nesting cannot grow.
  3. Compose is idempotent. A follow-up that already starts with the open tag is left alone.
⚠ Slash commands must never be wrapped. /model and friends are matched as exact or prefix text downstream, and an envelope in front would break the match and leak markup to the agent. isBuiltInSlashCommand (line 23) gates the compose step.

The quoted body is capped at 2000 characters and flagged with truncated="true", which renders a localized "quote was cut" label. The cap is a named constant, not an inline literal.

3Send path, before and after

The submit path keeps its shape. One step is inserted between reading the composer and calling onSubmit, and it runs in the same transaction that clears the draft.

Attachment sending keeps its own path. sendMessageWithAttachments appends its files prompt after the composed text, so a reply with an attachment carries both the quote and the file list (use-chat-submission.ts:30).

4State owner and lifecycle

One store owns the armed quote, keyed by conversation id, with exactly two writers: setReplyQuote from the Reply action and clearReplyQuote from dismiss or submit. That follows the repo rule that durable frontend state has one named owner and one obvious writer.

ⓘ The persisted quote is sanitized on read (conversation-local-storage.ts:121). localStorage is user-editable, so a quote restored from it is treated as untrusted input, not as state the app wrote.

5Render path in the bubble

The bubble splits the message before rendering. The quote card renders above the body, and only the follow-up feeds the existing truncation measurement.

// chat-message.tsx, user bubbles only
const reply = type === "user" ? splitReplyFromText(message) : null;
const bodyText = reply ? reply.body : message;

Extraction order is the whole point. UserMessageBody clamps at five lines, so a six-line quote left in the body would swallow the actual follow-up behind the "show more" control. Splitting first keeps the clamp measuring only what the user typed (chat-message.tsx:130).

⚠ The quote card renders markdown with raw HTML parsing off, always. A quote carries provenance context, and a user-sourced quote must not gain HTML privileges that the user's own bubble never grants (quote-card.tsx:20).

6Jump to the quoted message

Each bubble gains a data-event-id anchor carrying the source event id. Clicking a quote card calls useJumpToEvent, which scrolls to that anchor and highlights it briefly.

The target may not be mounted yet, so the hook loads older pages until it finds the anchor, bounded at ten pages. Past that bound it stops and surfaces a localized "message not in loaded history" hint instead of scrolling somewhere wrong (use-jump-to-event.ts:10).

ⓘ data-event-id is a product anchor, not a test hook. The E2E test uses it because a user click produces the same attribute, not because the attribute exists for testing.

7Where the Reply action appears

Reply uses the existing per-bubble hover actions slot in ChatMessage, so it inherits the positioning and keyboard behavior of its neighbours. Gating:

  • Main chat tab of a standard conversation only. Hidden in plan mode and on planning-agent bubbles.
  • Hidden on BTW messages and on pending "sending" bubbles, which have no event id yet.
  • Text only. An image-only message parses to an empty body and offers no Reply action.

There is no backend branch anywhere in this path. The quote is plain text, so Local, Cloud, OpenHands, and ACP agents all take the same route.

Residual risks worth a reviewer's attention:

  1. The envelope is visible to the model. That is the mechanism, not a leak: the model reads the quote as context. A user who types the open tag by hand gets a rendered card instead of literal text, which the idempotence rule accepts.
  2. Two writers on one store. Both are guarded by conversation id, and the store clears on submit inside the same callback that reads the composer.
  3. Jump depends on paging. A quote older than ten loaded pages resolves to a hint rather than a scroll. Raising the bound is a one-constant change.

Deliberately out of scope: selecting a range instead of the whole message, threads, and a protocol-level reply_to_event_id. The last one belongs to software-agent-sdk and can replace this envelope later without a data migration, since a message body stays readable either way.
