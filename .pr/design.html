One MCP editor, with existing connections intact

Customize → MCP Servers becomes the only visible MCP management page when the deployment serves Canvas. The Settings entry disappears. Existing servers remain in the same member-scoped storage and appear in Customize without copying credentials or recreating connections.

No new data migration. No iframe or handoff screen. Old bookmarks replace the current document with /canvas/mcp?org=…. Deploy the enterprise and Canvas changes together before retiring the old entry.

Ownership: frontend/src/hooks/use-settings-nav-items.ts removes the Settings link when agent_canvas_available is advertised. frontend/src/routes/settings.tsx::clientLoader redirects old bookmarks before consuming their organization parameter, carrying the explicit or currently selected org into Canvas. Storage continuity and safe naming

BeforeAfter
Both editors use /api/v1/settings. The older form cannot name remote servers and can discard fields it does not understand.Canvas reads the same saved map, including non-catalog servers and original keys. No automatic renaming or copying between users or organizations.
Canvas renaming rejects masked credentials; personal cloud profile references are not rewritten.POST /api/v1/mcp/servers/{name}/rename accepts {new_name, server?}. A member-row lock protects the config and personal profile-reference update in one transaction. A name-only edit sends no config or credential and performs no connection test or OAuth reauthorization.
A failed cloud settings request returns defaults and can look like an empty installed list.The error reaches the query. MCP shows retry and withholds editing until settings are read successfully. Retries are bounded.

server/routes/mcp_servers.py::rename_mcp_server resolves the authenticated user and effective organization, preserves the encrypted member storage boundary, restores submitted masks for combined edits through existing settings validation, and returns only the new name. It updates personal mcp_server_refs, preserving IDs, active selection and unknown profile fields. Case-insensitive name collisions return 409; a missing entry returns 404.

Existing auth state, headers, environment variables, secret references such as ${SONAR_TOKEN}, enabled state and timeouts stay with the server. The legacy agent_settings_diff.mcp_config fallback is read through effective_mcp_config; normal storage upgrades still apply. No global or organization-wide config is imported into a member’s collection.

Renaming is explicit. Scripts or automations containing a literal server name must be updated by their owner; the form explains this. Running conversations retain their launch-time configuration. New names are validated across all transports; unchanged legacy names are retained.

Deployment and local compatibility

The Helm chart derives AGENT_CANVAS_AVAILABLE and its structured web-client equivalent from Canvas being enabled with ingress. This is a deployment capability, not a new customer-facing toggle. Installations without Canvas keep their existing editor; supported OHE installations with Canvas expose only Customize. The SaaS/OSS app-mode distinction is not used to infer self-hosting.

Canvas’s new rename operation uses the cloud App API transport and selected org. Local Canvas keeps its existing typed Agent Server settings API and profile synchronization. Its rename guard now checks the edited configuration, so replacing or clearing a stored credential permits a rename; any remaining redacted credential still blocks it. There is no new Agent Server endpoint, SDK dependency or minimum-version increase. The shared validation changes apply to both local and cloud forms. OpenHands and ACP consume the same saved MCP map; conversation payload construction is unchanged.

Rollout order: release enterprise API support, release the matching Canvas, pin both in the deployment bundle, then enable the derived capability. An older enterprise backend cannot provide the new atomic rename endpoint; do not ship the Canvas rename change to those backends without coordinating the enterprise upgrade. Existing values stay intact if a request fails.

For older enterprise validation environments, build on the installed enterprise revision if main contains newer migrations. Preserve the database and provider configuration, and verify exact deployed images and restoration.
