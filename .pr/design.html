Bug fix · Agent Canvas

Chat attachment upload fails with 422 path must be inside the conversation workspace

Uploading any attachment (e.g. a .zip) could be rejected by the agent-server's workspace guard because Canvas guessed the conversation's working directory instead of reading the one the runtime actually stored. This PR makes the destination authoritative by reading it from the runtime, and turns the leftover guard rejection into a readable message.

1What changed

★ Key takeaway. The upload destination is now derived from the conversation's own workspace.working_dir (read via ConversationClient.getConversation) instead of a locally-guessed default. When the guess diverged from the stored value, the guard rejected every file with a 422; now the destination matches what the guard compares against.

Net effect: 2 behavior changes in one file, plus a new i18n string. Compatibility is additive — no public API, wire contract, or persisted shape changes; the local resolution is retained as a lazy fallback, so the WUP-001 behavior is unchanged whenever the runtime read is unavailable.

Base bf483c1 · 6 files · +235 / −17 (incl. tests + design doc).

2The bug, in one call chain

uploadFilesToConversation built the upload path from a locally resolved working dir, while the agent-server independently resolved the same conversation's stored working_dir against its own process CWD. Two resolvers, one comparison — any divergence lands the destination outside the workspace and trips bind_local_conversation_runtime.

3Fix 1 — read the working dir from the runtime

New helper readRuntimeWorkingDir (conversation-file-upload.api.ts:88) calls ConversationClient.getConversation(conversationId) against the target runtime and returns its workspace.working_dir when that value is absolute, or null otherwise (no value, a relative value, or any failure). A relative value is not adopted because the guard resolves it against the server's own CWD, which Canvas cannot reproduce. The call site prefers it and falls back to resolveConversationUploadWorkingDir:

// conversation-file-upload.api.ts:149 (after)
const workingDir =
  (await readRuntimeWorkingDir({ conversationUrl, sessionApiKey }, conversationId)) ??
  (await resolveConversationUploadWorkingDir(conversationId, currentConversation));
ⓘ The fallback is lazily evaluated (?? on the awaited result), so when the runtime answers, the local resolver's own network read is skipped entirely. An early draft passed it eagerly and a throwing fallback aborted the upload before the runtime was consulted — the live harness caught that regression, hence the current shape.
⚠ Scope: this fixes the destination, not the server's stored value. A relative runtime working_dir is ignored in favour of Canvas's own local resolution, so Canvas stops adopting a value it cannot resolve identically to the guard.

4Fix 2 — readable message for a leftover guard 422

If the guard still fires (e.g. a server-persisted relative dir), the raw HTTP request failed (422 …): {"detail":"path must be inside …"} is replaced by FILE_SERVICE$UPLOAD_WORKSPACE_MISMATCH via friendlyUploadError (conversation-file-upload.api.ts:175).

Before

// raw error surfaced to the user
HTTP request failed (422 ): {"detail":
 "path must be inside the conversation
 workspace"}

After

// i18n key, 15 languages
"Could not place the file inside this
 conversation's workspace. Reload the
 conversation and try again."
