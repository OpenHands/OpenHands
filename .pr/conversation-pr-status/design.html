Design doc · Issue #19030

Show the PRs a conversation produced, and their real state

The conversation overview's "Pull Requests" row counted the repository's first 30 open PRs, whatever the conversation did. This PR replaces that with the conversation's own PRs, read from GitHub with lifecycle, checks, review and conflict state kept separate, and adds a delivery badge to conversation-list rows. Every outcome the provider can't answer is shown as an explicit "unknown" state.

Frontend only · no Agent Server or SDK contract change · GitHub supported, other providers explicitly "unsupported"

1The count was the repo's, not the conversation's

★ Before, useRepositoryPullRequests listed pulls?state=open&per_page=30 for the whole repository (git-provider-items-service.ts:274), and the overview showed its length (conversation-overview-git-section.tsx:84). On a real backend, a conversation whose branch has one PR showed 30. Now it shows 1, with that PR's status. Start review at getConversationPullRequests.
ⓘ The drawer opened from that row (ConversationOverviewPullRequestsPanel) and the list badge (ConversationPullRequestIndicator) read the same service through the same query hook, so all three surfaces agree.

2New service; repo-wide PR list removed

3A PR belongs to a conversation by number or branch, never by text

SourceWhenRuleCode
trackedConversation has pr_number (Cloud)Fetch those numbers in the conversation's repository; de-duplicate; first 10, rest counted in omittedCount.:305
branchNo pr_number (always the case on Local, see agent-server-adapter.ts:428)pulls?state=all&head=owner:branch. A PR whose head is the repo's default branch is skipped: working on main is not evidence of authorship.:295
noneNeitherNo request at all.—

The branch is the workspace's checked-out branch when the local git probe sees the same repository, else the branch picked at start; a detached HEAD is ignored (use-active-conversation-pull-requests.ts:20). The agent usually works on a branch it created, so the start branch alone would miss its PR.

ⓘ Every PR is confirmed by a provider read. A PR number that GitHub cannot return stays in the list as "unknown" with the reason, rather than being trusted or dropped. Nothing is parsed from agent messages, per the triage criteria.

4Four states, each read from GitHub

FieldSourceRuleCode
lifecyclepulls/{n}merged_at → merged; closed → closed (without merging); else draft / open.:182
checkscheck-runs + commit statuses for the head SHAAny failure → failing (certain). Else any unreadable or unfetched result → unknown. Else any running → pending. Else passing, or none if there are no checks at all.:155
reviewpulls/{n}/reviewsEach reviewer's latest approve / request-changes decision; dismissals clear it, comments don't count. Any changes-requested wins.:166
conflictsmergeable, mergeable_stateOnly for open PRs; null (GitHub still computing) → unknown; merged / closed → not applicable and not rendered.:188
★ "Passing" is never inferred from a partial read. If GitHub reports more check runs than one page holds and none of the fetched ones failed, the answer is "unknown", because an unfetched run could still fail.

Access problems are classified in accessProblemOf: rate-limited (403/429 with x-ratelimit-remaining: 0), auth failed (401), forbidden (403), not found or not visible (404, which is how GitHub answers for private repos the token can't see), or error.

The list badge stays separate from the run-status dot, so a finished conversation with an open PR whose checks fail shows both. Failing and pending checks get their own icon beside the lifecycle text, so the state never depends on colour alone (:95).

8Risks and follow-ups

  1. GitHub rate limit. Four requests per PR, at most 10 PRs per conversation, cached 60 s and shared between the overview, drawer and badge. Unauthenticated GitHub allows 60 requests an hour; a rate-limited answer is shown as such, not as "no PRs". Local backends use a GITHUB_TOKEN secret when one exists, as the issue list already did.
  2. Local rows get no list badge. The local adapter always sends an empty pr_number; recording PRs for local conversations would be an Agent Server change, out of scope here.
  3. Not shown yet: "pushed without a PR" and "uncommitted changes" as row states. They can't be told apart reliably from list data; proposed as a follow-up rather than guessed.
  4. GitLab, Forgejo, Bitbucket: explicit "unsupported" until their status APIs are added; the service's result type already allows it per provider.
  5. Narrow rows: the badge takes space from the repo and branch chips, which then truncate. Moving it to its own line, like the model chip, is an easy change if reviewers prefer it.
  6. Automation runs: out of scope per the triage section; AutomationRun carries no run → PR link.
