Design doc · PR #19965 · fix/session-key-storage

Session keys scoped to the tab

Backend records keep their shape, but the durable copy of remote session keys and cloud tokens is gone: the persisted registry record is written blanked, and the real key is mirrored to tab-scoped sessionStorage. A reload re-hydrates; a fresh tab re-prompts.

1Why the durable key copy had to go

src/api/backend-registry/storage.ts was the single read/write boundary for backend records, and it wrote whatever it was given — including apiKey — straight to localStorage under openhands-backends storage.ts:95-118 (before). localStorage is durable, on-disk, and shared across tabs of the same origin, so a remote agent-server session key or a Cloud device-flow token outlived the tab it was entered in.

★ The fix removes the durable, cross-tab, on-disk plaintext copy — not the key from the running session. The tab keeps working; a new tab asks again.
⚠ This does not defend against script running on the canvas origin, which can read any key the page itself uses. That boundary is documented in the module (session-key-store.ts threat-model note).

3The policy owner: session-key-store.ts

One new module owns every decision (src/api/backend-registry/session-key-store.ts); storage.ts stays the single read/write boundary and calls into it storage.ts imports.

SymbolDecision it owns
shouldPersistApiKeyInRecordWhich keys may stay plaintext in the record: loopback locals and MARS guest records (the guest key is a public bundled constant). Everything else is governed.
syncSessionApiKeysMirrors real keys into sessionStorage["openhands-session-keys"] keyed by backend id before the record is written blanked.
readSessionApiKeyRe-hydrates the in-memory key for the tab on read; empty for a fresh tab.
isLoopbackUrlMoved here from storage.ts (was storage.ts:42-50 before) so the policy and its predicate live together.

Legacy migration happens in one pass inside readStoredBackends storage.ts:118-150: plaintext key → mirror, record rewritten blanked, all fields preserved.

4Compatibility and trade-offs

  • Record shape unchanged — apiKey stays a required string; validation and existing fixtures untouched.
  • Fresh tab re-prompts — the existing ApiKeyEntryScreen / health "needs attention" flows already handle an empty key; they now get a real reason to fire. Intentional per the issue acceptance.
  • Loopback/MARS-guest unchanged — local dev and the guest key keep working exactly as before.
  • Cookie-auth cloud records unchanged — they never carried a secret.
