Design doc · PR #19967 · fix/one-send-path

One shared user-message payload builder

Both send paths now call the same buildUserMessageContent / buildUserMessagePrompt builders, so a retried message carries exactly the payload the original send carried — including file_urls, which the retry path used to drop.

1Two send paths, one of them dropping attachments

On main the WebSocket path built its payload in conversation-websocket-context.tsx conversation-websocket-context.tsx (before) while the REST path built its own in agent-server-conversation-service.api.ts agent-server-conversation-service.api.ts (before), and only one of them ran the augmentation in send-message-with-attachments.ts send-message-with-attachments.ts (before). The pending-retry send went out without file_urls.

★ A retried message must be behaviorally identical to the original send — same text, same attachments, augmentation applied exactly once.

2Before → after: payload construction

3Scope: transports deliberately stay separate

Per the finding's scope-out, the two transports (WebSocket vs REST conversation service) are untouched — only payload construction is unified. chat-interface now passes raw text; the shared builder applies the prompt augmentation once, so the double-augmentation hazard of the old arrangement is structurally gone.

4Evidence and tests

  • Targeted suites (real run committed under .pr/one-send-path/send-path-tests-output.png): send-message-content.test.ts (81 new lines) + send-message.test.tsx — 18/18 passing: payload parity across both paths, single augmentation application, attachment forwarding on retry.
  • Plain-text sends are byte-for-byte unchanged (pinned by the same suites).
