Conversation overview diff stats: quadratic → linear

The conversation overview computes per-file line counts by walking the original and modified text. The walk asked "does this modified line still appear later in the original?" with originalLines.slice(originalIndex).includes(line) — which copies the suffix array and scans it on every step. On a 20 921-line file that is ~0.9 s of blocking work per file; on the reported lockfile-sized diffs it froze the UI. This PR replaces the suffix scan with a decrementing multiset of the lines the walker has not consumed, making membership O(1) while returning byte-identical counts.

2Code before / after

before (main)

// membership = copy the suffix + scan
if (
  modifiedIndex < modifiedLines.length &&
  (originalIndex >= originalLines.length ||
    !originalLines.slice(originalIndex).includes(modifiedLine))
) {
  additions += 1;
  modifiedIndex += 1;
  continue;
}

after (this PR)

// counts of lines not consumed yet
const remaining = new Map<string, number>();
for (const line of originalLines) {
  remaining.set(line, (remaining.get(line) ?? 0) + 1);
}
const hasRemaining = (line: string) =>
  (remaining.get(line) ?? 0) > 0;

The two branches that consume an original line now decrement the map:

// equal-line branch and deletion branch both call:
consumeOriginal(originalLine);

3Why the counts stay identical

The old test was originalLines.slice(originalIndex).includes(x). That is exactly count of x in originalLines[originalIndex:] > 0. The map is seeded with the full multiset and decremented on every step that advances originalIndex, so at the top of each iteration it holds exactly the multiset of originalLines[originalIndex:]. The two membership tests are therefore equivalent for every input, and the walk visits the same branches in the same order.

No output change. Duplicate lines are the only place a naive "seen before" set would diverge; a counting multiset matches the suffix scan even when the same line appears many times.
