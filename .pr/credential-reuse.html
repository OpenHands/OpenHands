Reuse ChatGPT authorization.
Make Codex onboarding explicit.

ChatGPT OAuth and API-key-free Codex usage already exist. The draft adds a Codex ACP setup path that provisions credentials for the subprocess. Shared LLM/ACP credentials are proposed here and remain unimplemented.

Decision for review: keep the existing subscription OAuth login as the owner; add one encrypted, versioned server record and consumer adapters. Sharing a rotating refresh token requires proven coordination with native Codex refresh before it is enabled.

1 · OAuth is existing; ACP onboarding is the gap

The existing LLM Profile flow authenticates the SDK LLM transport. Codex ACP consumes auth.json or CODEX_AUTH_JSON. The current draft wires CodexAuthCard into SetupAcpSecretsStep and Agent settings. It does not automatically reuse an LLM-profile login.

4 · An old LLM login may need reconnection for Codex

OAuthCredentials currently omits an ID token, and _complete_device_login drops that part of the provider response. The proposal retains the genuine provider-issued ID token; it never fabricates one from access-token claims.

Existing stateProposed migration
Complete Codex credentialImport for the same backend/user into the encrypted record; project the existing SDK LLM fields.
LLM credential without ID tokenKeep LLM access usable. Retain an ID token if a normal provider refresh returns one; otherwise request reconnection when Codex is enabled.
Explicitly disconnectedPersist a tombstone/revision. Restart or host-file discovery must not resurrect access.

5 · Sharing must preserve disconnect and refresh ownership

ActionProposed behavior
Disconnect CodexDisable ACP provisioning and invalidate its binding; retain a still-enabled LLM consumer.
Disconnect LLMDisable that consumer without unexpectedly disconnecting Codex.
Sign out everywhereExplicitly disable both consumers, cancel pending/refresh work and remove the token record.
Last consumer disabledRemove tokens but retain revocation state; stale completions cannot reconnect.
Refresh gate: CAS prevents stale writes, but does not prevent two runtimes from refreshing the same rotating token concurrently. Native Codex file refresh/writeback and SDK refresh need coordinated ownership verified with the pinned ACP runtime.

If safe shared refresh cannot be established, share the UI/transport and retain explicitly separate authorizations. Copying a rotating token into two independently refreshed stores is not the proposed solution.

Existing integration points: ACP file lifecycle:125 · restart_for_updated_credentials:2031.

7 · Land SDK ownership before the Canvas consumer

  1. SDK/Agent Server: full-response retention, encrypted owner, migration, consumer disconnect and real refresh concurrency tests.
  2. TypeScript client: typed safe status and challenge contracts; no token-bearing browser payload.
  3. Canvas: one shared login component/status owner across LLM profiles, Codex onboarding and Agent settings.
  4. Official SDK/client/server release, exact Canvas pins and minimumAgentServer, then outstanding real-account/Docker/remote acceptance.

Required coverage: both reuse directions, missing ID token, restart, backend/account isolation, native ACP rotation versus SDK refresh, disconnect/global sign-out and stale completion. No release number is invented. This PR remains draft pending architectural agreement and implementation.
