# Maritime provider

Add Backend → Providers → **Maritime** creates OpenHands agent-servers on the user's [Maritime](https://maritime.sh) account and connects Canvas to them. Available in the Electron desktop app, and in the web build when the Canvas server hosts the bridge (`MARITIME_WEB=1`, see "Web build").

A Maritime _agent_ is a Firecracker micro-VM running a container image, with its own persistent disk (`/data`, which Maritime sets as `HOME`). Every agent with an exposed port gets its own public HTTPS and WebSocket hostname, `https://<agent-id>.mtm.sh/` (`webUrl`). Maritime sleeps an idle agent with its memory kept and wakes it on the next HTTP request. So unlike DigitalOcean there is no tunnel and no proxy: the renderer registers the agent's hostname as an ordinary `kind: "local"` backend with the agent-server's session key.

- **The image**: `ghcr.io/maritime-sh/openhands-agent-server:<versions.agentServer>`, the published `ghcr.io/openhands/agent-server:<version>-python` image with a launcher that binds `$PORT`. Maritime routes an agent's hostname to `$PORT` (18789 today, injected by Maritime for `framework: "custom"`), and the stock image binds 8000; that is the whole difference. Built and published from [maritime-sh/openhands-agent-server](https://github.com/maritime-sh/openhands-agent-server) for each agent-server release. `config/defaults.json` → `maritime.imageRepository`; the tag is `versions.agentServer`, so Canvas creates the agent-server version it pins. `MARITIME_IMAGE_REPOSITORY` / `MARITIME_IMAGE_TAG` / `MARITIME_API_BASE_URL` override. The Docker image has no `config/` beside its scripts, so it falls back to `:latest`.
- **Create** (`createAgent` in `scripts/maritime-bridge.mjs`): `POST /api/agents` with `framework: "custom"`, the image, `exposedPort: 8080` (Maritime's routed port), `publicWeb: true`, `externalId: "openhands-agent-canvas"`, the chosen `memMb` (vCPUs follow: one per 2 GB), `idleTtlSeconds` 1800, and secret env vars `OH_SESSION_API_KEYS_0` and `OH_SECRET_KEY`, both generated in the bridge, plus `OH_ALLOW_CORS_ORIGINS_0` when the Canvas origin is not loopback (the agent-server always allows loopback). The body is built in the trusted process; the renderer contributes a name, a memory size and its origin (the web bridge replaces the origin with the request's own). The call then polls `GET /api/agents/{id}` until `active`. The renderer waits for the agent-server itself with `waitForMaritimeAgentServer` (the same settings + server-info check the Add Backend form runs) before registering.
- **Why `publicWeb`**: a private Maritime agent URL needs a Maritime link cookie, which a browser never sends on a CORS preflight. The agent-server's session key guards a public one, as on every remote backend. Never create an agent-server without `OH_SESSION_API_KEYS_0`.
- **Session keys**: Maritime stores secret env vars encrypted and only shows them masked, so the key generated at create cannot be read back. The bridge keeps it per agent in its credential store (`scripts/maritime-credentials.mjs`), and `listAgents` reports `hasAccessKey`. An agent without one (created on another machine, or the store was lost) offers **Set new access key** instead of Open: `resetAccessKey` writes a new `OH_SESSION_API_KEYS_0` (`POST /api/agents/{id}/env`, needs the `secrets` scope) and restarts the agent (`POST /restart`); conversations and settings survive on `/data`, running work stops, so it sits behind `ConfirmationModal`. Sign-out drops the API key only, not session keys.
- **Open**: `openAgent` starts a sleeping or stopped agent (`POST /start`), polls until `active`, and returns `{agentId, name, host, sessionApiKey}`. `useMaritimeAgentActions` registers or re-points the backend whose `maritimeAgentId` matches, makes it active and lands in the latest conversation, like `useConnectMarsSession`.
- **Sleep and delete**: Sleep (`POST /sleep`) keeps memory and is not confirmed; any request wakes the agent again. Delete (`DELETE /api/agents/{id}`) removes the VM and its disk, so it is confirmed; the bridge forgets the session key and the renderer removes the agent's backends, only after Maritime accepted the delete.
- **Cost**: every HTTP request to an agent's hostname wakes it and resets Maritime's idle timer, and open WebSocket frames do not count as activity (a busy CPU does). `useBackendsHealth` therefore probes non-active Maritime backends once, without interval or focus refetches, exactly like MARS sessions. Do not add background polling of agents the user is not on.
- **Errors**: Electron IPC keeps only an error's message, so `scripts/maritime-api.mjs` (`describeMaritimeFailure`) writes messages that stand on their own: 401 rejected key, 403 missing scope, 402 Maritime's plan-limit text, 429 awake cap, and Maritime's own `detail` otherwise. The panel shows them as they are.
- **Credentials**: the Maritime API key (`mk_...`, created at https://maritime.sh/settings/api-keys with the provision, deploy, secrets and manage scopes; Maritime requires manage to delete an agent) never reaches the renderer. It is verified with `GET /api/v1/account/limits` before it is kept. Desktop: one record encrypted with Electron `safeStorage` in `maritime-credentials.json` under the app's user data. Web build: the same `SecretStore` the DigitalOcean bridge uses (keychain, a file encrypted with `OH_SECRET_KEY`, or memory) under `<state dir>/maritime`. The bridge reports `storage` and `isSaved` so the panel can say where the key is kept.
- **Web build**: `scripts/maritime-web-bridge.mjs` exposes `POST /maritime/rpc/<method>` (exactly the `MARITIME_IPC` methods) and `GET /maritime/health`, mounted by `scripts/ingress.mjs` and `scripts/static-server.mjs` only with `MARITIME_WEB=1`. It shares the DigitalOcean bridge's guards (`scripts/web-bridge-guards.mjs`): the session key (`MARITIME_WEB_KEY`, else the server's `--session-api-key`) on every RPC as `X-Session-API-Key`, loopback-only without a key, cross-origin and foreign-`Host` requests refused. `MARITIME_API_KEY` signs it in at startup. The dev launchers place it like the MARS bridge (`buildMaritimeWebEnv`), and `src/api/maritime/maritime-web-bridge.ts` installs a fetch-backed `window.maritimeBridge` from `entry.client.tsx` after probing `/maritime/health`.
- **Tests**: `__tests__/scripts/maritime-{api,bridge,web-bridge}.test.ts`, the "Maritime" blocks of `__tests__/components/backends/add-backend-modal.test.tsx` and `__tests__/scripts/dev-static.test.ts`, and `__tests__/api/maritime-web-bridge.test.ts`. Component tests fake `window.maritimeBridge`, not the hooks.
- **Limits**: a Maritime agent publishes one port, the agent server's. VS Code and the worker ports are not reachable, and the image runs no automation server, so Automate (scheduled and event-driven automations) is unavailable on a Maritime backend; Canvas sees `/api/automation/*` answer 404 there, as on any agent server started without one.
