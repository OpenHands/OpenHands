# DigitalOcean Managed Agents (MARS)

Available in the Electron desktop app and in the web build (the server hosts the bridge; see "Web build" below). A DigitalOcean *agent* is an immutable Agent Config (DigitalOcean's console calls it an environment); a _session_ is a microVM launched from one, running an OpenHands agent-server with its own disk and conversations.

- **Surfaces**: the "Choose how you want to connect" chooser (`AddBackendChooser` in `backend-form-modal.tsx`) gains a third **DigitalOcean** tab, `DigitalOceanConnectPanel`: sign in (OAuth or token), then pick an OpenHands agent — opening it resumes the agent's latest live session or launches its first, and closes the modal. Each agent row expands to list its sessions as children (any connectable one opens directly), and **New Agent** (`DigitalOceanNewAgentForm`) creates an OpenHands Agent Config and launches its first session. While a MARS backend is active, `MarsSessionPanel` (`src/components/features/sidebar/mars-session-panel.tsx`) replaces the sidebar conversation list: the agent's sessions read like thread folders (the current one expands to its conversations, others open with a click), the header "+" launches a new session, and the agent menu switches agent or opens `ManageBackendsModal initialView="managed-agents"` — the full management view in `src/components/features/backends/managed-agents/`. Everything is gated on `getMarsBridge()`: Electron's preload provides it, and the web build gets a fetch-backed one from the Agent Canvas server when that server hosts the MARS web bridge (below); a page with neither never shows it.
- **OpenHands only**: agent configs are shown only when their manifest's `agent` is `openhands` (flat `agent:` or `spec.agent`). The list endpoint omits manifests, so `listAgentConfigs` in `scripts/mars-tunnel-bridge.mjs` fetches each config once (configs are immutable) and adds `agent`. The match is strict: a manifest without `agent: openhands` (older specs that no longer launch) or one that could not be read (`agent: null`, retried on the next list) is hidden. Sessions are shown only when their `config_id` names a matching config; `agent_kind` is not used, since OpenHands sessions report `AGENT_KIND_UNSPECIFIED`.
- **New Agent**: `createOpenHandsAgent({name, size?})` in `scripts/mars-tunnel-bridge.mjs` posts `POST /v2/agents/configs` `{name, manifest_yaml}` with the manifest from `buildOpenHandsManifest()` (`scripts/mars-api.mjs`): flat `agent: openhands` + `template: openhands` + `keep_warm: false`, plus `size:` when one is chosen. No LLM key goes into the manifest; the LLM is set up in the session's agent-server (Settings → LLM) after connecting. The manifest is built in the main process, not accepted over IPC, so the renderer can only create OpenHands agents (same reasoning as pinning the guest port). Keep `template` explicit — harness-api has no agent kind that derives an OpenHands template. Names follow harness-api's rule (`isValidAgentName`: 1–64 of `[A-Za-z0-9._-]`, alphanumeric at both ends).
- **Sandbox size**: the New Agent form's "Sandbox size" picker lists `GET /v2/agents/sessions/sandbox/sizes` (`listSandboxSizes`, `useMarsSandboxSizes`; static, so `staleTime: Infinity`) and initially selects the smallest listed VM (vCPU count, then memory), regardless of catalog order. The explicit “Default (DigitalOcean picks)” option stays available; selecting it omits `size`. A user choice is not replaced when the catalog updates. The chosen slug goes into the manifest as a top-level `size:` line (slug-validated in `buildOpenHandsManifest`), because sessions created from a config cannot carry a size; it therefore applies to every session of that agent. While the catalog is pending, empty or failed, no size is selected automatically. Creation waits for a concrete size or an explicit choice of the DigitalOcean default, so an unavailable catalog cannot silently opt the user into an unknown VM size.
- **Shared hooks**: `useLaunchMarsSession()` (open / launch / create agent / "open agent", with create-vs-connect error copy) and `useMarsSignIn()` (sign-in, switch connection, sign-out) back the chooser tab, the Managed Agents view and the sidebar; reuse them instead of calling `createSession` + connect directly.
- **Port-forward tunnel**: `openTunnel` opens the port-forward tunnel and, on desktop, returns `{transport: "tunnel", host: http://127.0.0.1:<port>}`; the renderer registers that host as an ordinary local backend. The public ingress URL path (direct connection to `GET /v2/agents/sessions/{id}/ingress`) was built and tested here and then removed from this branch on 2026-10-08 — REST worked over it but its WebSocket is reset inside the platform (microVM LB → activator, fix in microvm#1920) — and will come back once that is deployed.
- **Web build (browser)**: the server that fronts the web build (`scripts/ingress.mjs` for `npm run dev`, `scripts/static-server.mjs` for `dev:static` and Docker) hosts the same bridge via `scripts/mars-web-bridge.mjs` and exposes it same-origin: `POST /mars/rpc/<method>` (an explicit allow-list of the `MarsBridge` surface, `RPC_METHODS`; `src/api/mars/mars-web-bridge.ts` installs a fetch-backed `window.marsBridge` from `entry.client.tsx` after probing `GET /mars/health`), and `/mars/sessions/<id>/…` as an HTTP + WebSocket reverse proxy to the tunnel listener the server holds for that session (through the bridge's own `createProxyHandlers` instance: no idle/response timeout, since agent-server calls can stay silent for minutes, no `X-Forwarded-*`, and upstream failures answer a JSON 502 `{error:{message}}`; the tunnel client itself pings the harness socket every 30 s). `openTunnel` therefore answers `host: <origin>/mars/sessions/<id>`, a path-prefixed backend; proxied JSON has agent-server URLs (`conversation_url` and friends) rewritten to that prefix so the event WebSocket lands on the proxy. This is what makes the browser work at all: harness-api has no CORS, the tunnel needs a Node process, and the token must stay off the page. The routes are **mounted only with `MARS_WEB=1`, when a key is configured or on a loopback bind** (`MARS_WEB=0` keeps them off; both dev launchers set it on the static child so only the browser-facing ingress hosts a bridge, and Electron passes `marsWebBridge: false` so none runs there) and want the server's session key on every request: the renderer sends it as `X-Session-API-Key` on `/mars/rpc/*` and gets an `HttpOnly; SameSite=Strict; Path=/mars` cookie back, which the browser attaches on its own to the proxied REST calls and the WebSocket upgrade (the one request a browser cannot put a header on). An upgrade with neither key nor cookie (an agent's SDK or TypeScript client) is accepted and must send the key as its first message, `{"type":"auth","session_api_key":…}`, within 10 s; only then does the bridge dial the session and relay both ways, keeping the login frame (the guest agent-server takes no key). `openTunnel` also prepares the sandbox (`scripts/mars-sandbox-prep.mjs`: the guest's missing `OH_SECRET_KEY`, and the terminal moved off tmux) once per session per process, before it answers, so every caller gets a prepared sandbox. The agent-facing guide is `docs/DIGITALOCEAN_AGENTS.md`; keep the five calls it documents (`listAgentConfigs`, `listConfigSessions`, `createSession`, `openTunnel`, `pauseSession`) working. The key is `MARS_WEB_KEY`, else the server's `--session-api-key` (`dev-with-automation` hands the stack's key to `ingress.mjs`); with neither, `mountMarsWebBridge` mounts only on a loopback bind, where a `Host` check stops DNS rebinding. Only `conversation_url` fields are rewritten (a URL inside a message is content), JSON past 8 MB streams through untouched, `Cookie` and the key header never reach the session host, a malformed session path is a 400, an upstream WebSocket the browser abandoned mid-handshake is terminated, and `dispose()` closes both ends of every proxied WebSocket. Credentials survive a restart (see **Auth**; `MARS_TOKEN` seeds one at startup), the cookie is an HMAC of the key (so it outlives a restart and dies with a key rotation), Sign-in with DigitalOcean works from the page (see **Auth**); its return route `GET /mars/oauth/callback` is the one route besides `/mars/health` that needs no key, because the browser arrives from DigitalOcean without the `SameSite=Strict` cookie. Cross-origin requests are refused.
- **Stop and delete are confirmed, destructive, and gated**: Stop (`destroySession`) ends the session and its sandbox through `DELETE /v2/agents/sessions/{id}`, detaching any live connection first; Delete agent (`deleteAgentConfig`) soft-deletes the config through `DELETE /v2/agents/configs/{id}`. harness-api does not refuse a delete while sessions run, so the renderer only enables it once none of the agent's sessions is live (paused counts as live). Both sit behind `ConfirmationModal` and ride the same IPC / web-RPC surface as pause. In a session row the main action (Connect / Resume and connect / Open) is rightmost with Stop directly left of it. Removing a MARS backend in Manage Backends opens `MarsBackendRemovalModal` instead of the generic confirmation: "Disconnect only" (the session keeps running and billing) or "Stop session" (destroy first, then remove; a refused destroy keeps the backend and shows the error), and Manage Backends ignores Escape / outside clicks while it is open.
- **One backend per session**: connecting registers an ordinary `kind: "local"` backend named after the session (`buildMarsBackendName`) whose `host` is the loopback tunnel (in the web build, the server's `/mars/sessions/<id>` proxy), carrying `marsSessionId` / `marsConfigId`. The backend record persists while tunnels and (in the web build) credentials do not, so `useRestoreMarsTunnels` reconnects the active MARS backend once a usable DigitalOcean connection exists — after sign-in, not before — and Manage Backends keeps a MARS backend selectable while its health is red, since selecting it is what reconnects it. The far end is a real agent-server, so conversations, files, and the terminal work unmodified. Connect logic is shared through `useConnectMarsSession()` (`src/hooks/use-connect-mars-session.ts`), which lands the user in the session's most recent conversation (or a new chat) with the URL pinned to the new backend.
- **Server-side ownership**: tunnels, the harness-api REST client, OAuth, and credentials live in a Node process — the Electron main process on desktop, the web server in the web build (`scripts/mars-tunnel-bridge.mjs`, `tunnel-client.mjs`, `tunnel-registry.mjs`, `mars-api.mjs`, `mars-oauth.mjs`, `mars-credentials.mjs`) — and reach the renderer only via `window.marsBridge` (`electron/preload-main.cjs`, or `/mars/rpc/*`). harness-api sends no CORS headers and tokens must never reach the page, so do not move these calls into the renderer.
- **Fail fast, explain why**: the tunnel records the last upstream failure (`getTunnel().upstreamFailure`). `waitForMarsAgentServer` throws `MarsAttachError("refused")` immediately on close code 4001 or HTTP 401/403, and `MarsAttachError("not-openhands")` when close code 4002 (guest dial failed — nothing on :8000) outlasts a 20 s grace window, since a just-woken sandbox also closes 4002 while booting. `getMarsConnectErrorMessage` maps both to `DO_AGENTS$ERROR_*` copy.
- **Cost**: every probe and tunnel dial counts as sandbox activity and keeps it from auto-pausing. `useRestoreMarsTunnels` reopens only the *active* backend's tunnel, and `useBackendsHealth` probes non-active MARS backends once without interval/focus/reconnect refetches. Do not add background polling of sessions the user is not on.
- **Auth**: OAuth is the authorization-code grant with PKCE (`scripts/mars-oauth.mjs`; DigitalOcean no longer offers the implicit grant, and a public client keeps no secret). The PKCE verifier never leaves the bridge. On desktop, `signInWithOAuth` opens the system browser and takes the return on a one-off `http://127.0.0.1:<any port>/callback` listener. In the web build the page calls `beginSignIn` (the server picks the return address: the page's own origin on a loopback host, else `http://127.0.0.1:<port>/mars/oauth/callback`, which a remote device cannot open, so the user pastes that address into `completeSignIn`), then `awaitSignIn` until the return lands. An attempt works once and expires after ten minutes. Access tokens last an hour; the bridge refreshes one a minute before it expires, one refresh per connection at a time (a refresh token works once; Canvas processes sharing a store take a lock file beside it, `scripts/mars-lock-file.mjs`), and a grant DigitalOcean refuses asks for sign-in again: any 400 or 401 from the token endpoint counts, since DigitalOcean answers a spent refresh token with `invalid_request`, not `invalid_grant`. A grant nothing keeps any more (a sign-in that failed after the exchange, or one a new sign-in to the same team replaced) is revoked. Personal access tokens always work, behind "Use a personal access token instead" when OAuth is offered. The public client ID comes from `DO_OAUTH_CLIENT_ID`, else `mars.oauthClientId` in `config/defaults.json` (empty = PAT only; DigitalOcean matches loopback return addresses on any port, so the client registers `http://127.0.0.1/callback` and `http://127.0.0.1/mars/oauth/callback`, plus the `localhost` and `[::1]` forms); `MARS_API_BASE_URL` / `mars.apiBaseUrl` select the harness API. Desktop credentials are `safeStorage`-encrypted (session-only when the OS keychain is unavailable); web-build credentials live where `scripts/mars-secret-store.mjs` puts them: the macOS Keychain (`/usr/bin/security`) or the Secret Service (`secret-tool`) on the host running Canvas, else a file encrypted with `OH_SECRET_KEY`, else memory (`OH_CANVAS_SECRET_STORE` forces one). The secrets go to those tools on stdin, never as arguments. The list of connections sits beside them in `digitalocean/mars-credentials.json` under `MARS_STATE_DIR` (default: the Canvas state folder, `~/.openhands/agent-canvas`) and never holds a token. The bridge reports `storage: {kind, label, host}` and each connection's `isSaved`, so the UI can say where the sign-in is kept, or that it is not; after a token is verified, `GET /v2/account` names its team and email, and a team already listed keeps its connection id.
