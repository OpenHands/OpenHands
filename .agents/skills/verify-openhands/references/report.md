# Verification report contract

Keep the complete ledger private until reviewed. Use stable relative artifact
paths; do not publish localStorage, authentication headers, live keys, session
URLs, system messages or raw traces. An ARIA/DOM snapshot can contain a password's
value even when its screenshot shows only bullets.

## Run identity

Record run ID and UTC interval, repository, BASE/TARGET full SHAs, baseline report,
checkout cleanliness, build command, Node/browser/OS/font/theme versions, backend
SDK and automation versions, actual ports, authorization/spend scope, and selected
backend/platform capabilities. Explain bootstrap or comparison gaps.

## Coverage ledger

Use one row per exercised or required sub-feature and entry point. Do not roll up
one passing example into a pass for its whole family.

| Feature/check + entry point | Revision/backend/viewport | Action or command | Expected → actual | Result | Evidence |
|---|---|---|---|---|---|

Use `pass`, `fail`, `blocked`, or `not-run`. For blocked rows name the missing
prerequisite, attempted action, and next step. Identify checks outside the declared
scope separately; do not count them as passed. Report denominator and counts for
both feature families and individual checks. A layout-only inspection must say so.

## Change / intent ledger (weekly)

| Commit / merged PR | Paths → feature IDs | Documented intent (quote/link) | Baseline → target observation | Intent status | Classification / issue |
|---|---|---|---|---|---|

Intent status: documented / undocumented / contradictory. Runtime classification:
intended-change / introduced-in-range / reproduced-on-both /
observed-origin-unconfirmed / environment-or-harness-gap. Keep these independent.
A screenshot proves appearance, not provenance or a side effect; include reloads,
real files, actual run status, or read-only state as appropriate.

## Findings and verdict

Lead with scope and verdict, then actionable defects and intent gaps. Include exact
steps, observed dimensions/error text, severity/impact, issue links, and baseline
confidence. Link side-by-side images at the same viewport; mark intentional visual
changes with the approving PR. Count browser exceptions even if the UI recovered.

Record maintenance corrections separately from product failures. Note CI status
without relabeling it live proof. Do not modify human-authored PR sections.

## Teardown and next baseline

List fixture cleanup, owned-process/port shutdown, and retained artifact locations.
Verify at least one retained evidence file after shutdown. Name the next proposed
baseline, its coverage limits, and who accepted it; never overwrite the prior
accepted baseline automatically. Raw private logs are not baseline screenshots.

External publication requires authorization and an attribution such as:
“This report was generated by an AI agent (OpenHands) on behalf of the requester.”
