# F28 — Automation setup page

The setup page is the one form for making and changing automations outside the
template dialog. **Add Automation → Create Automation** opens it blank at
`/automations/setup`; a saved draft reopens at `/automations/setup?draftId=<id>`;
kebab **Edit** opens an existing automation at
`/automations/setup?automationId=<id>`. The form collects Name, a Prompt (or
Custom Python with entrypoint and setup script), model (LLM profile) and
repositories, a Schedule or Event trigger, and optional plugins and timeout,
in three cards: **Trigger**, **Action** and **Settings** (Name, Timeout). The
page header is the one the automation detail page uses: a back arrow (to the
dashboard, or to the automation in edit mode), the title, the save state and the
toolbar. A docked composer under the form can ask the agent to fill it. Create mode's
toolbar has **Save draft**, **Test** and **Create Automation**; edit mode's has
**Test**, **Save** and **Close**. A server-backed draft carries the server's
validation result and test runs; Create turns it into a real, enabled
automation and removes the draft.

F22 keeps `F22.agent-assisted-setup` (the end-to-end agent, plugin, phone and
draft-Test recipes); F23 owns edit mode (`F23.edit-*`, including Test and the save state on the edit
page). This family gives each create-mode behavior its own ID so a pass can fail one without
failing the others.

Source: `src/routes/automation-setup-new.tsx`, `src/components/features/automations/setup/` (`automation-setup-panel.tsx`, `automation-setup-prompt-stack.tsx`, `automation-setup-draft-service.ts`), `src/utils/automation-repo-sources.ts`, `src/utils/automation-event-sources.ts`, `src/api/automation-form-client-tool.ts`, `src/hooks/use-start-automation-setup.ts`, `src/hooks/use-open-automation-editor.ts`.

## Sub-features

- `F28.open-blank`: Create Automation opens `/automations/setup` with Name pre-filled **New Automation** (placeholder `Standup digest`), an empty Prompt, Schedule selected with Daily at `09:00` in `America/New_York` (the default, whatever the browser's time zone), the docked composer (`Need help creating an automation?`) and no new conversation. The save state already reads **Unsaved changes** and the toolbar **Test** is disabled; the header's back arrow (`automation-page-back`) links to `/automations`. Both kinds show the LLM profile pill `automation-setup-model` (Prompt inside the prompt card, Custom under **Entrypoint and setup**) beside an **Agent profile** pill (`automation-setup-agent-profile`, `None`) when the automation service supports agent profiles for that kind (`presetAgentProfiles` for Prompt and Plugin, `agentProfiles` for Custom; the pinned local automation lists both), and the Schedule and Event cards read `Run on an interval or at a set time` and `Run when an integration or webhook sends an event`.
- `F28.custom-agent-profile`: on the Custom kind, when the automation service lists `agentProfiles` in its capabilities `features` (the local automation does), an **Agent profile** pill (`automation-setup-agent-profile`, `None` by default) sits beside the LLM profile pill; its menu lists `None` and every saved agent profile with the LLM profile it runs on. Picking a profile locks the LLM profile pill to that profile's LLM profile (a lock icon whose tooltip reads `Set by the <name> agent profile. Choose None to pick an LLM profile.`); **None** unlocks it. Save draft saves the draft with that `agent_profile_id`, and **Create Automation** creates the automation with it (`model` `null`).
- `F28.preset-agent-profile`: on the Prompt kind (also with a plugin added), when the automation service lists `presetAgentProfiles` in its capabilities `features` (the pinned local automation does), the prompt card holds an **Agent profile** pill (`automation-setup-agent-profile`, `None`) before the LLM profile pill; its menu lists `None` and every saved agent profile with the LLM profile it runs on. Picking a profile locks the LLM profile pill to that profile's LLM profile (the same lock icon and tooltip as on the Custom kind). Save draft sends `agent_profile_id` with `endpoint` `/v1/preset/prompt` (`/v1/preset/plugin` once a plugin is added), and **Create Automation** sends `POST /api/automation/v1/preset/prompt` with `agent_profile_id` and no `model`; the detail page's Action card reads **Agent profile** `<name>` and **LLM profile** `<its LLM profile>` **From agent profile**. Kebab or header **Edit** shows the saved profile in the same pill; choosing **None** and Save sends `agent_profile_id: null`. A run of that automation starts its conversation from the profile (`launched_agent_profile.agent_profile_id`). A service that advertises only `agentProfiles` keeps Prompt and Plugin on the LLM profile pill alone, and an OpenHands Enterprise (self-hosted) instance that turns agent profile selection off shows no Agent profile pill on any kind.
- `F28.kind-toggle`: the button beside the Prompt label switches between Prompt and **Custom** (Custom Python). Custom shows a generated Python script that calls `AUTOMATION_CALLBACK_URL`, and **Entrypoint and setup** reveals Entrypoint `python3 main.py`, Setup script path `setup.sh` and a no-op setup script; the LLM profile pill stays below the script, and the profile picked there is saved with the draft as `model` (left on **Active profile**, nothing is sent). Switching back shows the Prompt again.
- `F28.schedule-presets`: in create mode the Frequency control (the same control as on the edit page, whose presets and saving F23 owns as edit-schedule and edit-cron) starts on Daily at `09:00`, and switching presets fills create-mode defaults: Once a date-time at the next whole hour today, Weekly Monday, and Custom the cron of the preset it replaces (from Weekly, Monday at `10:30` it reads `30 10 * * 1`; Weekdays `30 10 * * 1-5`, Hourly `0 * * * *`, Once on 17 October at `09:00` `0 9 17 10 *`). Clicking Custom again keeps a cron already typed there; leaving Custom for a preset and coming back starts from that preset again. Weekly shows the weekday before the time. Under a Custom cron a plain-language preview (`automation-setup-custom-schedule-preview`) reads it back, such as `Every Monday at 10:30 AM`. Every preset keeps the 13-entry time zone select.
- `F28.event-trigger`: choosing **Event** replaces the schedule with Event source (default **GitHub**, sent as `github`; its menu lists, by name, the event sources the automation service reports in `eventSources` (Azure DevOps, Bitbucket Data Center, GitHub, Jira Data Center when built-in sources are enabled), or, when it reports none or has not answered, the automation service's built-in providers GitHub, Azure DevOps, Bitbucket Data Center and Jira Data Center, plus **Custom**), Event key (default `issue_comment.created`, free text; an arrow beside it opens the selected source's event types, see event-types-by-source below, and is absent when the source has no catalog), **Add Filter** (one free-text filter input), **Ask Agent**, the notice `Event sources need a public URL to deliver webhooks to this instance.`, and a **Test event payload** pre-filled with a JSON object for that source and key. A source the backend has not registered (menu **Custom**, then a typed name such as `linear`, `slack`, `gitlab` or `jira`) adds **Register this as a custom webhook source**, checked by default; a typed known source (`jira_dc`, `bitbucket_data_center`, `azure_devops` with the fallback list) shows its name (`Jira Data Center`) and no such section. The Event source menu closes on an outside click, a choice or Escape; Escape sets the toggle's `aria-expanded` back to `false` and returns focus to the toggle, at desktop and phone widths. Save draft sends the trigger as `{"type":"event","source":<source>,"on":<key>,"filter":<filter>}`; where the automation service has no event delivery for that source (a local stack) the draft is saved with `dispatchable: false` and the draft bar reads `No event delivery is configured for 'github' events in this deployment.` (`event_source_not_configured`), yet **Create Automation** creates it, inactive, with that trigger; its detail page's Trigger card reads `GitHub · <key>` with the filter.
- `F28.event-types-by-source`: the Event key arrow (`automation-setup-event-key-toggle`) opens a menu (`automation-setup-event-key-menu`) of the selected source's whole catalog from the service's `eventTypesBySource`, whatever the field holds (a typed concrete key such as `issue.created` filters nothing out and is not changed by opening): GitHub `issue_comment.*`, `issues.*`, `pull_request.*`, `pull_request_review.*`, `push`, `release.*` (and `workflow_run.*` on automation services that parse it); Jira Data Center `comment_created` … `jira:issue_updated`; Bitbucket Data Center `pr:comment:added` … `repo:refs_changed`; Azure DevOps its `git.pullrequest.*` and comment types where the service reports them; a source without a catalog (a custom source) has no arrow. Picking an option sets the key, closes the menu and returns focus to the arrow; Escape, a second arrow click or an outside click closes it without changing the key (Escape returns focus to the arrow, `aria-expanded` `false`); the menu fits a 390 px screen. Typed keys and comma-separated patterns stay editable. Choosing a source that does not deliver the current key switches the key to that source's first type (back to GitHub that is the pattern `issue_comment.*`); a source without a catalog keeps the key. The untouched default test payload follows the source: Jira Data Center sends `webhookEvent`, Bitbucket Data Center `eventKey` set to the key, other sources `{source, event, action: "test"}`; an edited payload is kept. A picked Jira DC `comment_created` or Bitbucket DC `pr:opened` saves as `trigger: {type: "event", source: "jira_dc", on: "comment_created"}` / `{source: "bitbucket_data_center", on: "pr:opened"}`. A service that reports no event sources (the pinned local automation) offers no suggestions at all.
- `F28.timeout`: **Add Timeout** adds an optional **Timeout seconds** number field with a remove button; `1800` saves and the draft reads **Ready to test**.
- `F28.draft-save`: **Save draft** works on any form, valid or not; the first save replaces the URL with `?draftId=<id>`, shows the **Draft saved** bar (relative time, **View test runs**, **Test**) and the toast `Draft saved in this conversation.`, and the save state reads **Saved just now**. The draft appears in the dashboard Drafts group (F21).
- `F28.draft-validation`: the server validates on save, not on blur. An invalid draft is still saved (`dispatchable: false`) and its first error replaces **Ready to test** in the draft bar: an empty prompt shows `Field required` (also under Prompt), a bad custom cron shows `Value error, Invalid cron expression: every day`. A field error stays until the next save. **Test** stays enabled on a saved invalid draft: it saves again, opens **Test runs** with the same error in a red alert and dispatches nothing. The current validation error comes before any test status: after a successful draft Test the pill reads **Latest test passed**, and once an invalid cron is saved it reads the cron error (also after a reload, at desktop and phone widths) while the API marks the draft non-dispatchable.
- `F28.draft-save-error`: a draft the server refuses outright (a timeout above 1800 returns `422`) sets the save state to **Save failed** and shows one error toast with the reason the API gives (a timeout of 1801 reads `Value error, timeout must not exceed 1800 seconds (30 minutes)`). The draft bar drops its validity pill (no stale **Ready to test**) until a save succeeds.
- `F28.required-before-test`: Test and Create check locally first and send nothing when a required field is empty: `Add a prompt before continuing.` (Prompt or Plugin kind), `Add a plugin source before continuing.`, `Add Python code before continuing.`, `Add an entrypoint command before continuing.`, `Add a setup script path before continuing.`, `Add a setup script before continuing.`; an event Test with a payload that is not a JSON object shows `Enter a valid JSON object before testing this event automation.` A blank Name is not an error: it is derived from the prompt.
- `F28.test-gated`: in create mode **Test** stays disabled until the draft is saved and unchanged since; editing any field after a save disables it again until the next **Save draft**.
- `F28.draft-test`: **Test** on a saved, valid draft opens **Test runs** (with **Back**), shows `Test run started.` and a Pending row; it runs a hidden disabled copy of the draft, not a dashboard automation. Expected: the row reaches Successful or Failed by itself. Known failure #18263 (reproduced again 2026-10-27 on a Custom Python draft, automation 1.26.0): the row stays Pending and the page does not poll the runs after the first request. Known failure (reproduced once 2026-10-17, SDK1.55.1, [OpenHands/software-agent-sdk#6024](https://github.com/OpenHands/software-agent-sdk/issues/6024)): gracefully restarting an owned deferred-init Agent Server during the Custom Test command can leave its persisted BashCommand without final BashOutput. Reopening Test runs → View logs showed `RUNNING` / `(no output)`; two postrestart BashOutput searches returned zero. Expected: an interrupted command retains terminal status/output and Logs stops implying it is running. This is the shared F23/F28 RunLogsModal consumer; native Terminal, SIGKILL, phone and fix attribution were not verified.
- `F28.create`: **Create Automation** creates the automation (a Custom Python automation is created on, with the model picked in its LLM profile pill; a Prompt or Plugin automation is created off, with an **Inactive** badge), navigates to `/automations/<id>` (a Custom Python automation shows **Script**) with the toast `Automation created.`, and removes the draft from the dashboard Drafts group.
- `F28.repositories`: on the Prompt kind, **Repositories** **+** (`automation-setup-repository-add`) opens a menu with **Search repositories** and **Custom**. Custom opens **Add Repositories** (`Repository`, placeholder `owner/repo`, **Add** disabled until something is typed); each address becomes a chip with a remove button. The draft and the create request send `owner/repo` as `{url, provider: "github"}` and a full URL (`https://gitlab.com/...`) without a provider; the detail page's Action card lists both under Repositories as `owner/repo`. With no Git provider connected on a local backend the menu lists no repositories and an info icon beside **+** explains `Configure a provider token secret, e.g. "GITHUB_TOKEN", in the Settings page to see repo options.` The row and its menu fit at 390 px. The **+** menu and the model pill's popover (`automation-setup-model-popover`) close on Escape, also when focus is in the menu's **Search repositories** field: `aria-expanded` goes back to `false` and focus returns to their trigger. An outside click also closes them.
- `F28.repository-providers`: with a connected Git provider the menu lists its repositories (`automation-setup-repository-option-<name>`) and searches the provider. Each option stays on one line: when a name does not fit, the organization/project part shortens with an ellipsis first so the repository name stays visible, and the option's hover title is the full name. With more than one connected provider whose repositories the automation service clones (`repoProviders` in `/api/automation/v1/capabilities`; 1.26.0 lists Azure DevOps, Bitbucket, GitHub and GitLab), a **Git provider** choice (`automation-setup-repository-provider`) switches lists, GitHub first. A GitHub pick is stored as `owner/repo`; other providers' picks as the URL on their host, a connected self-hosted host also sending its `provider`. A connected provider the service does not clone, or one whose host the server does not report, shows `Automations can't clone <provider> repositories yet.` (`automation-setup-repository-unsupported`).
- `F28.error-contrast`: the draft bar's error pill and the Test runs error alert use the theme's error color (`text-feedback-error`) and reach at least 4.5:1 in all five color themes. Their tints follow the same theme error color: the pill a 5% tint over the draft bar surface, the alert a 10% tint with a 40% border.
- `F28.ask-agent`: on the create page, **Ask Agent** in the Event section starts the setup conversation: the URL becomes `/conversations/<id>` (the setup split view), its first user message is the canned `Help me set the event trigger. Ask what should start this automation, then fill the event source, event key, and any event filter.`, and the form keeps the values already entered (name, event key). At phone width the page lands on the **Form** view (`automation-setup-mobile-view-form` pressed) with those values; the message and the reply are under **Conversation**, and returning to **Form** shows the same values. Known failure (reproduced 2026-11-05, not reproduced 2026-11-07, [#19363](https://github.com/OpenHands/OpenHands/issues/19363)): at phone width, switching from **Conversation** back to **Form** shows a reset form (Name `New Automation`, **Schedule** selected, no event key): the mobile form unmounts on the switch and the entered values are dropped.
- `F28.assistant-event-sources`: a setup conversation's system message tells the agent that it is an automation setup session, to propose the automation by filling the form and not to create, update, enable, run or delete automations, drafts or custom webhooks through the automation API. The setup assistant's `automation_form_update` tool describes this deployment's event sources from the automation service's capabilities: each reported source with its event keys (and, for Jira and Bitbucket Data Center, a tested event key and filter); with no reported sources (a local stack, `eventSources` `[]`) it says `This deployment delivers no webhook events, so event triggers are unavailable: use triggerKind "cron".`; when the capabilities cannot be read it tells the assistant to ask which integration delivers the event. Its `repository` field is described for every git provider (GitHub, GitLab, Bitbucket Cloud or Data Center, Azure DevOps).

## How to get to it (user POV)

- Dashboard header **Add Automation → Create Automation** (`automations-add-automation`, then `automations-add-automation-create`): blank create mode. Every create recipe below starts here.
- Empty dashboard **Create Automation** (`automations-empty >> automations-create-automation`): the same blank form (`F21.empty-state`).
- Dashboard Drafts group: name or **Resume** (`automation-setup-draft-resume-<draft-id>`) and the pencil (**Edit**, `automation-setup-draft-edit-<draft-id>`) open `?draftId=<id>`.
- Kebab **Edit** on a dashboard card or the detail page header: edit mode (`?automationId=<id>`, `F21.edit`, `F23.edit-open`).
- A direct URL with `draftId` or `automationId` (see the cold-load gotcha).

## Driving it with control-openhands

Preconditions:

- Baseline state (`launch`, `doctor`, `onboard --skip`). No LLM is needed except for the Ask Agent bullet, which starts two short setup conversations: every other bullet uses the Custom Python kind or never dispatches, and the rest of the agent-assisted path stays in F22.
- Desktop viewport; the `F28.error-contrast` bullet switches color themes (Settings → Application, `F16`) and restores the default.
- `control-openhands llm preset deepseek` (or `--no-validate`) has saved `deepseek-flash` and `deepseek-pro`: the Custom kind bullet picks `deepseek-pro` in the model pill. No model call is made.
- Blocked here: `F28.repository-providers` (a connected Git provider with a real token; the provider choice needs two connected providers the automation service clones). The pinned local automation lists `bitbucket_data_center` in `repoProviders` and accepts it in a draft's `repos`.
- The Event types by source bullet needs an automation service that reports built-in event sources and `eventTypesBySource`: OpenHands/automation `main` after #653 (no release up to 1.26.1 has it) with `AUTOMATION_WEBHOOK_SECRET` set. `control-openhands launch` does not pass that variable to the service, so run a second stack with `--automation-path <clone>` on a scratch clone of that commit whose `ServiceSettings.webhook_secret` default (`openhands/automation/config.py`) is a dummy value, and record the run as fault injection. `api GET /api/automation/v1/capabilities` then lists `eventSources` `["azure_devops","bitbucket_data_center","github","jira_dc"]`.
- The original recipes were run on 2026-10-16 on a fresh local `control-openhands launch` of main with Agent Server 1.55.1 and no LLM; the blank-form, presets and error-contrast recipes were run again on 2026-10-17. The dated 2026-10-17 maintenance evidence separately proves the added regression checks. Every recipe except the blocked Git provider choice was run again on 2026-10-27 with Agent Server 1.58.1 and automation 1.26.0. Documented known failures remain failures.

## Gotchas

- The Ask Agent prompt is fixed and does not forbid tools: with the `openhands-automation` skill loaded, deepseek-flash usually runs a few read-only `curl` calls against the run's own automation service (`/api/automation/v1/capabilities`, `/v1/webhooks`) before asking what should start the automation. That stays inside the run; pause the conversation if an action reaches anything else.
- A toast can cover the toolbar (Save draft, Test, Close) and stays while the pointer rests on it, so the next toolbar click times out ("subtree intercepts pointer events"). After each save, `browser hover` a form field (for example `testid=automation-setup-name`) before clicking the toolbar again, as F22's Gotchas say.
- Drive inputs with `browser fill`: setting `.value` from `browser eval` does not reach React state for every field, and a save then sends the old value.
- Change one field per Save draft when checking a validation message: a save shows only the first server error, so two edits in one save hide the second.
- A cold load of `/automations/setup?draftId=<id>` or `?automationId=<id>` (a reload or a typed URL) opens the form: re-checked 2026-10-14 on a `control-openhands launch` of main with this family (both read their Name back). An earlier instance of unknown build stayed on **Loading saved draft…** for more than 20 s; if that returns, compare with opening the same draft from the dashboard.
- The draft bar duplicates the prompt error: `Field required` appears both under Prompt and in the bar.
- Kebab **Edit** on a Custom Python (tarball) automation shows the **Existing code bundle** summary, not the code editor, and Save keeps that bundle without asking for upload-time fields (`F23.edit-open`, `F23.edit-save`).
- With no menu open, Escape on the setup page does nothing, by design (`F23.edit-close`); it closes only an open Repositories **+** menu, model or agent profile popover, Event source menu or Event key menu.
