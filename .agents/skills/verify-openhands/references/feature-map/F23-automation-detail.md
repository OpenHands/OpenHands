# F23 — Automation detail, runs and editing

The detail page (`/automations/<id>`) shows one automation: a **Back to
Automations** link, a header with the name, an **Active**/**Inactive** badge,
**Run now**, an on/off switch and a kebab (Export, Tarball, Edit, Turn on/off,
Delete); a **Why this is paused** banner when it was turned off; the Prompt (or,
for a script automation, the Script bundle); Configuration (repositories,
trigger, schedule or event source/type/filter, LLM profile); a **Plugins** card
when it has plugins; an Activity card (Created, Last run);
and the **Activity Log** of runs with status, summary, cost, a logs dialog, a
link to each run's conversation and JSON/CSV export. Kebab **Edit** opens the
setup page in edit mode (`/automations/setup?automationId=<id>`),
which changes name, prompt, LLM profile, repositories, timeout and the trigger; it has no
agent profile control, and saving keeps any agent profile already stored on the
automation. A
DRAFT-state test automation (materialized by a draft Test, F21.saved-drafts)
shows a **Draft** badge and no on/off switch.

Source: `src/routes/automation-detail.tsx`, `src/components/features/automations/detail/`, `src/hooks/use-open-automation-editor.ts`, `src/utils/automation-edit-draft.ts`, `src/utils/automation-state.ts`, `src/components/features/automations/setup/automation-setup-panel.tsx` (edit mode), `src/components/features/automations/delete-confirmation-modal.tsx`, `src/hooks/query/use-automation-detail.ts`, `src/utils/automation-preset-sources.ts`, `src/hooks/query/use-bash-command-logs.ts`, `src/hooks/query/use-automation-tarball-files.ts`, `src/utils/automation-schedule.ts`, `src/utils/automation-disabled-reason.ts`, `src/utils/automation-activity-log-export.ts`.

## Sub-features

- `F23.open-detail`: a dashboard card, a list row, the kebab **View** and a direct URL open `/automations/<id>`; browser Back from a run's conversation returns to it.
- `F23.back-link`: **Back to Automations** (on the page and on the not-found state) returns to `/automations`.
- `F23.loading`: `detail-skeleton` stands in while the automation loads.
- `F23.not-found`: an unknown id shows **Automation not found** with "The automation you're looking for doesn't exist or has been deleted." and the back link.
- `F23.backend-unavailable`: with the automation service down, the page shows **Automations Unavailable** and **Retry**; Retry recovers once the service is back.
- `F23.load-error`: when the health check is still good but the automation request fails, the page shows **Failed to load automations** and **Retry**.
- `F23.header`: the header shows the name, the Active/Inactive badge, **Run now** (disabled while inactive), the switch (`Turn on`/`Turn off`) and the **Automation actions** kebab with Export, Tarball, Edit, Turn on/Turn off and Delete. A DRAFT-state test automation shows a **Draft** badge (`active-status-badge-draft`), no switch, no paused banner and a kebab without Turn on/off.
- `F23.toggle`: the header switch flips the enabled flag at once (no confirmation); the badge, switch and Run now follow and survive a reload.
- `F23.disabled-reason`: after **Turn off**, the banner `automation-disabled-reason-banner` reads **Why this is paused** / **Turned off manually** / **Paused <time>**; it is gone while active.
- `F23.run-now`: **Run now** dispatches a run with the toast **Automation dispatched** and a Pending row appears in the log (the button reads **Starting…** only for the few ms of the request).
- `F23.run-now-error`: a failed dispatch shows exactly one error toast with the API message; when the automation is gone (`Automation not found`), the page then shows the **Automation not found** state.
- `F23.run-status-polling`: while a run is Pending or Running the log refetches every 3 s, so Pending → Running → Successful/Failed, the run's live phase (`run-phase`: the service's free-form `current_phase`, such as `Installing dependencies`, `Agent is working on the task` or the agent's current action summary), the summary, the cost and the conversation link appear without a reload; the Activity card's **Last run** updates too.
- `F23.activity-log`: **Activity Log** shows **No activity yet** with Export disabled before the first run, then one row per run (newest first): start time, summary, cost (`$0.0000` format, `run-cost`), a logs icon, status badge (`run-status-icon-<status>`). A Pending, Running or Failed row with a reported phase shows it beside the badge (`run-phase`, as sent, clipped with the full text on hover); a Failed row keeps its last phase, and Successful or Cancelled rows show none.
- `F23.run-task-outcome`: a Completed run whose agent finished with a task outcome other than success shows that outcome instead of **Successful**: `blocked` and `partial_success` read **Blocked** / **Partial** with `run-status-icon-warning`, `unknown` and any unrecognised status string read **Needs review** (`run-status-icon-needs-review`), and a finish response without a string `status` (summary only, custom fields only, a non-string status, or not an object) is expected to read **Successful**, and an `outcome_summary`, when it has one, is still shown (#17682); the row summary is the agent's `outcome_summary`, and the Logs dialog's Task section repeats it.
- `F23.activity-log-more`: with more than 20 runs a **Load more** button grows the page by 20.
- `F23.run-no-conversation`: a finished run without a conversation reads **No Conversation**; only a script run (no agent) gets "No conversation — this run executed a script. Use View logs for its output."
- `F23.run-linked-conversation`: a run row with a conversation is a link labelled `View conversation for run at <time>` to `/conversations/<conversation_id>`, whose title is `<automation name> — <UTC timestamp>`.
- `F23.run-logs-modal`: the row's terminal icon (**View logs**) opens the **Logs** dialog with Run, Task (status, summary, `automation-task-metadata`) and System sections and Output/Error tabs showing the run command's stdout/stderr; Escape and the X close it without navigating.
- `F23.debug-with-openhands`: in the Logs dialog of a **Failed** run, **Debug with OpenHands** starts a conversation seeded with the automation, the error and the run id, and opens it.
- `F23.activity-log-export`: **Export JSON** / **Export CSV** download `<name-slug>.activity-log.json|csv` with every run, including `conversation_url` and `phase` (the run's `current_phase`).
- `F23.run-deeplink`: `?run=<runId>` highlights that run (`automation-run-highlight-<runId>`, class `bg-focus/10`) and scrolls to it; an unknown run id highlights nothing.
- `F23.prompt-collapse`: a prompt taller than about 10 lines is clipped to 240 px with a fade (`automation-prompt-fade`) and **View More**; **View Less** collapses it again.
- `F23.configuration`: a cron automation shows Trigger **Schedule**, the Schedule and **LLM profile** (`Active profile` or the profile name).
- `F23.configuration-event`: an event automation shows Trigger **Event**, **Event Source**, **Event Type** and **Filter**, truncated at 60 characters with **Show more**/**Show less**.
- `F23.plugins-repo`: an automation created with repositories and plugins shows **Repositories** (one `owner/repo` row each, with a branch badge for its ref) and a **Plugins** card with one chip per plugin.
- `F23.script-section`: a script (tarball) automation shows **Script** with the entrypoint and the bundle's files in place of the Prompt.
- `F23.export`: kebab **Export** downloads `<name-slug>.automation.json` (`version`, `kind: "automation"`, `spec`); an automation's first repository and its plugins go into `spec` as `repository`, `branch` and `plugins`.
- `F23.tarball`: kebab **Tarball** downloads the automation's code bundle.
- `F23.delete`: kebab **Delete** asks `Delete "<name>"? This cannot be undone.`; Cancel keeps it, Delete removes it and returns to `/automations`.
- `F23.edit-open`: kebab **Edit** opens the setup page `/automations/setup?automationId=<id>` (#17688; the **Edit automation** modal is gone) prefilled with Name, Prompt, the LLM profile picker (no agent profile picker), the trigger (Schedule with Frequency, or Event), timezone and Timeout seconds, with **Test**, **Save** and **Close** in the toolbar and a docked composer; no conversation exists until a prompt is sent. A script (tarball or bundle) automation shows `Custom Python` with the **Existing code bundle** summary (`automation-setup-existing-bundle`, the upload id) instead of a code editor.
- `F23.edit-close`: **Close** leaves without saving and lands on `/automations` (the dashboard, not the detail page); Escape does nothing on the page.
- `F23.edit-validation`: an empty prompt is refused with the toast **Add a prompt before continuing.** (no request); a bad cron, a cron that never runs or a timeout above 1800 is sent to the API, refused with `422`, and its message is the single error toast (`Value error, Invalid cron expression: not a cron`, `Value error, Cron expression cannot produce any future fire times: 0 0 31 2 *`, `Value error, timeout must not exceed 1800 seconds (30 minutes)`); nothing is saved.
- `F23.edit-save`: Save sends one PATCH (also when nothing changed), shows **Saving…** then **Saved just now**, the toast **Automation updated**, and the detail page and API reflect it; an Active profile model stays `null`. On a Prompt or Plugin automation the PATCH carries no `agent_profile_id`, so a profile stored on it stays unchanged; on a script automation it sends the stored `agent_profile_id` back. On a script (tarball or bundle) automation, including one without a `setup_script_path`, Save keeps the existing bundle: it asks for no setup script path, setup script or code, the PATCH carries no bundle fields, and `tarball_path`, `entrypoint` and `setup_script_path` read back unchanged; the summary stays after each edit and a reload.
- `F23.edit-repositories`: Edit lists the automation's saved repositories (`automation-setup-repository-value`, as stored: a full URL or `owner/repo`). When the automation service advertises `repoUpdate` (automation 1.25.1 does) and the automation is a Prompt or Plugin preset, **+** and each remove button change the list: Save sends `repos` only when the list changed (saved entries keep their branch and provider; an added `owner/repo` goes as `provider: "github"`), and the detail page, the API and a reopened Edit show the saved list at once. Without `repoUpdate` (automation 1.22.0) the row reads **Can't be changed for this automation** with no add or remove buttons and Save sends no `repos`.
- `F23.edit-test`: on the edit page **Test** dispatches the automation as last saved (`POST /api/automation/v1/<id>/dispatch`, no PATCH first) and shows `Test run started.` on the form; unsaved edits are not part of that run. Whether it should test the current form is a product decision (Gotchas).
- `F23.edit-dirty-state`: the edit page shows no save state for unsaved edits (no **Unsaved changes**, which create mode shows, F28); the label appears only while saving (**Saving…**) and after (**Saved just now** or **Save failed**). **Close** discards the edits.
- `F23.edit-schedule`: Frequency offers Once, Hourly, Daily, Weekdays (Mon–Fri), Weekly and Custom; Weekly adds **Day of week** and **At**; they are saved as a cron expression and read back after a reload. Switching to Custom starts the Custom field from the cron of the preset it replaces (Weekly, Wednesday at `10:30` → `30 10 * * 3`), and a saved cron that matches a preset reads back as that preset, not as Custom.
- `F23.edit-time-cleared`: clearing **At** on a preset schedule and saving should be refused with a message instead of being dropped or replaced. Known failure (reproduced 2026-10-13, [#17948](https://github.com/OpenHands/OpenHands/issues/17948) item, new symptom since #17688): Save silently stores midnight (`0 0 * * 3`) and toasts **Automation updated**; Save draft in the create flow stores `0 0 * * *` the same way. Open PR #18260 (head `0f812ac68902d2c71896568311bffb8aa6f216a6`, checked 2026-10-15) targets the live setup panel: it rejects an invalid or cleared time before Save and Save draft, with an edit-mode regression test. It is not merged; the known failure above remains the observed behavior on this map’s baseline.
- `F23.edit-cron`: a custom cron schedule shows Frequency **Custom** with an editable **Custom** cron field and a timezone select.
- `F23.edit-event-readonly`: for an event automation the edit page shows Event selected with Event source, event key and filter controls (editable now, no longer read-only text) and no schedule fields.
- `F23.edit-save-error`: a failed save shows exactly one error toast with the API message (`Automation not found` for an automation deleted meanwhile), the save state reads **Save failed** and the edits stay on the page; the toolbar **Test** on that page also toasts `Automation not found`.
- `F23.phone`: at 390×844 the detail page has no horizontal overflow, and the Edit page fits with its title, Test, Save and Close reachable. Below 640 px the header stacks: the name (wrapping when long) and badge on one row, then **Run now**, the switch and the kebab, all inside the viewport in LTR and RTL; a long name such as `QA_Inert_Event_Detail` keeps the switch and kebab reachable by pointer (LTR switch x≈136–176, kebab x≈184–216; document width 390). From 640 px up the name and actions share one row, actions on the right.

## How to get to it (user POV)

- Dashboard (`/automations`, F21): click a card's heading, a list row link, or the kebab **Automation actions** → **View**; a sparkline bar opens `/automations/<id>?run=<runId>` (F21.sparkline-deeplink).
- Direct URL `/automations/<id>` and `/automations/<id>?run=<runId>`. Get `<id>` from `control-openhands browser url` after opening a card, or from `control-openhands api GET /api/automation/v1`; get `<runId>` from `control-openhands api GET /api/automation/v1/<id>/runs`.
- Edit: the detail kebab **Edit** (exercised here) and the dashboard kebab **Edit** (F21.edit) both open `/automations/setup?automationId=<id>`; a cold load of that URL opens it too.
- Browser Back from a run's conversation returns to the detail page.
- The detail page has no command-menu entry and no keyboard shortcut.

## Driving it with control-openhands

Preconditions:

- Baseline state (launched, doctored, `onboard --skip` done) and an active LLM profile for the runs: `control-openhands llm preset deepseek` (`--api-key-file <file>` when the key is in a file); the edit recipes also expect `deepseek-pro` in the LLM profile list.
- No `QA_F23` automations and no **Daily news digest** exist (`control-openhands api GET /api/automation/v1`).
- Arrange three fixtures through the API (arrange only; F22 owns creating automations in the UI). Each prints the new automation in `body` (`body.id` is `<id>`):
  `control-openhands api POST /api/automation/v1/preset/prompt --write --data '{"name":"QA_F23 Pong","prompt":"Reply with the single word: pong. Do not run any tools.","trigger":{"type":"cron","schedule":"0 9 * * *","timezone":"UTC"},"enabled":false}'`,
  `control-openhands api POST /api/automation/v1/preset/prompt --write --data '{"name":"QA_F23 Fail","prompt":"Reply with the single word: pong.","trigger":{"type":"cron","schedule":"0 0 1 1 *","timezone":"UTC"},"enabled":true}'`,
  `control-openhands api POST /api/automation/v1/preset/plugin --write --data '{"name":"QA_F23 Event","prompt":"QA line 1: reply pong.\nQA line 2: reply pong.\nQA line 3: reply pong.\nQA line 4: reply pong.\nQA line 5: reply pong.\nQA line 6: reply pong.\nQA line 7: reply pong.\nQA line 8: reply pong.\nQA line 9: reply pong.\nQA line 10: reply pong.\nQA line 11: reply pong.\nQA line 12: reply pong.\nQA line 13: reply pong.\nQA line 14: reply pong.\nQA line 15: reply pong.","plugins":[{"source":"github:qa-example/qa-plugin"}],"repos":[{"url":"https://github.com/qa-example/qa-repo","ref":"main"}],"trigger":{"type":"event","source":"github","on":"pull_request.opened","filter":"pull_request.draft == `false` && pull_request.base.ref == repository.default_branch"},"enabled":false}'`.

## Gotchas

- The automations QA checklist (F28) expects edit-mode **Test** to run the current form state; the panel calls `dispatchAutomation(<id>)`, which runs the saved automation. `F23.edit-test` records current behavior; whether it should change is a product decision, not a map correction.
- The Logs dialog's panel keeps long content reachable (`F23.run-logs-modal`, #18175 / #18173). Re-verified 2026-10-17 (revision `04529073`, Agent Server 1.55.1) with a genuine 30-line `outcome_summary` at 1440×1000 and 390×844 (2026-10-13 also at 390×500): the panel is `testid=run-logs-body` (`max-h-[80vh]`, `overflow-y: auto`) with a sticky header (Logs + X stay visible); the Output box no longer scrolls on its own, the whole panel does, and its end (`=== RESULT === ALL_OK`) is reachable at the bottom. Verified 2026-10-10 on an independent fresh Linux Local stack at product revision `5a8c3832154b14d2dad651801c0ab3f74c96f02e`, SDK 1.54.0 and automation 1.19.3: a genuine DeepSeek finish produced a 4,596-character `outcome_summary` and 1,079-character metadata `message`; summary/metadata endings, Output/Error tabs and the true stdout end were reachable at 1440×1000, 390×844, 1440×500 and 390×500. The header/X remained visible, closing did not navigate, and phone had no horizontal overflow. Preserve those long-content and short-height checks when retesting. The verified scope is pinned Linux Local; macOS, Cloud and legacy/custom finish schemas need their own checks. `browser bbox 'role=dialog'` measures the full-screen wrapper, not the panel: measure the panel with `browser eval`.
- The detail page has no `main` landmark: `browser snapshot 'role=main'` times out. Snapshot the page, or scope by section headings (`role=heading[name="Configuration"] >> xpath=ancestor::div[2]`).
- The kebab menu has no test ids; `role=list >> has-text=Tarball` scopes the detail kebab (the dashboard kebab has no Tarball, so F21 uses `has-text=Export`).
- Kebab **Edit** (detail and dashboard) opens `/automations/setup?automationId=<id>`. The edit page's Save and Test report API failures with the API's message (see `F23.edit-validation`, `F23.edit-save-error`), and its `Automation updated` toast covers Test/Save/Close until the pointer moves away.
- Known defect: clearing **At** on a preset schedule and saving stores midnight with no message ([#17948](https://github.com/OpenHands/OpenHands/issues/17948) item; with the old modal it was silently ignored).
- On a local backend the Logs dialog reads every run's output from the server-level `/api/bash/bash_events/search`, with or without a conversation. It caches what it fetched: reload before checking its requests with `browser network`.
- Known defect: prompt runs also have a `bash_command_id`, so every row shows the logs icon, and a prompt run that ended without a conversation is labelled as a script run (`F23.run-no-conversation`) ([#17948](https://github.com/OpenHands/OpenHands/issues/17948)).
- The automation service (1.25.1 here) keeps repos and plugins only under `preset_metadata`; the UI reads them from there. Repositories show `owner/repo` without the host (a GitLab URL reads like a GitHub one), a repo without a ref gets no badge, and Export keeps only the first repository (all plugins). The **Notification** field reads a top-level `notification` that the service has no field for, so it never renders on a local stack (#16644 tracks removing or mapping it).
- The Schedule field shows the raw cron (`0 9 * * *`) and no timezone: the service returns no `schedule_human` and no top-level `timezone`, so the Edit dialog also omits its `Timezone:` hint.
- `run-phase` renders the service's `current_phase` string as sent (it is not translated, so it can read like the agent's own wording); the dashboard card, Home tooltip and pinned card use the same text.
- An LLM profile that does not exist (`model: "qa-no-such-profile"`) does not fail the run: it ran and succeeded with the active profile. Use timeout `1` to get a failed run; it takes several minutes to fail.
- `Load more` in the log (`F23.activity-log-more`) needs more than 20 runs of one automation; at about 35 s and one model call each it is left out of a normal pass (not-run).
- The script section needs a tarball automation. The account-free way to get one is F22's **Daily news digest** bundle entry (it uploads its bundle and creates the automation); the custom-automation **Upload tarball** action takes `control-openhands fixture tarball`. Its kebab Edit and a cold load of `/automations/setup?automationId=<id>` both show the **Existing code bundle** summary (see F21.edit, `F23.edit-save`).
- **Starting…** on Run now lasts only for the dispatch request (under 50 ms locally); `--observe` does not catch it.
- The run row is a plain `<a href>`, so opening a run's conversation reloads the whole app (a `document` request in `browser network`), unlike sidebar navigation.
- A 404 detail request is retried three times before **Automation not found** shows (about 7 s of skeleton) ([#17948](https://github.com/OpenHands/OpenHands/issues/17948)); wait with `wait-text`, not `count`.
- `browser fill` on the Timeout spinbutton with letters fails in Playwright and, after its 30 s retry, the dialog was found closed; use numeric values (`1.5`, `0`, `1801`) to reach the timeout errors.
- The Tarball download is named `<name>.tar` (spaces become `_`) but is gzip-compressed ([#17948](https://github.com/OpenHands/OpenHands/issues/17948)); `browser downloads --inspect` does not list tar entries, so inspect it with `tar -tzf`.
- **Debug with OpenHands** starts a real agent with the `openhands-automation` skill and the automation API key. It acts on live automations: here it looked up `QA_F23 Fail` by name (a newer fixture with the same name), PATCHed its timeout back to 600 and dispatched it, which adds runs and conversations.
